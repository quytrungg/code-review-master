# Leave domain review

Review rules for leave features: balances and corrections, accrual and tenure, requests and approvals, categories and policies, payroll synchronisation, reporting, and the scenario matrix a change has to cover. Each bullet is one rule; where a rule conflicts with the code under review, the code wins.

## Balances and corrections

- **Read the leave wiki before inferring leave behaviour from the code** — `https://github.com/Thinkei/leave-llm-wiki` is the maintained domain reference, and it already answers the routing questions that look like code questions: the resolution table in `wiki/apis/peo-leave-routing-contracts.md` puts the data organisation on `target_member.organisation` while the role check stays on the host `current_member`, and `wiki/integrations/peo-globalteams-leave-routing.md` says under Planning Risks that a host-organisation URL parameter is not evidence that Leave data belongs to the host member. Fetch the one page the change is about, at a pinned commit, and name both in the review; a delegated pass has no network, so it returns the question and the parent settles it. Read the page rather than the tree: the wiki is large and exactly one page is the authority for this change.

- **Make the leave-unit converter raise when it exhausts its iteration cap without reaching the requested units, instead of returning the partial `units_converted`** — a weeks-to-hours conversion that stops short returns fewer units than requested, so the request, the deduction and the balance disagree while the job reports success. Compare unit totals with a named epsilon tolerance at the validation site instead of rounding the stored units, and round only at display time: `total_units` is synced to the payroll provider with all its decimals, so rounding to 2 before storing changes what payroll receives and, in a shared parameter path, applies to every org. A 52.0000000156 total rejecting against a statutory 52 is a floating-point comparison that belongs in the validation as `EPSILON_TOLERANCE` (0.0001), with tests pinning both sides: 52.001 invalid, 52.0001 and 52.0000000156 valid.
- **Compute each paradigm's balance in its own calculator behind one factory that returns an object implementing a shared balance interface (`base_balance`, `projected_leave_balance`, ...), and keep region-specific methods out of the shared balance service** — a shared service carrying ANZ-only methods cannot absorb UK/CA/SEA calculations without per-country branches and methods only one region needs. One factory plus one interface per paradigm makes the supported surface explicit, so a new country is a new class rather than a new condition in every existing method — the class had become `FetchANZDetails` in all but name. The same shape already exists in the leave-settings domain (`LeaveSettings::CategoryDeletion::ParadigmFactory`).
- **Do not replace `Date.current` with a caller-supplied `as_at_date` in a leave-balance or balance-details path without proving the result against past and future dates, and state whether that date includes pending leave requests** — `as_at_date` may be a future or past date, so a balance that meant "today" silently becomes a projection, and pending requests outside that date drop out of the number. The `FetchHrDetails` as-at-date path came from backdated leave requests, and the same endpoint feeds the leave-request form, where a balance that shifts by a day is wrong money on the form.
- **Choose the balance paradigm from the member's own payroll state, not from the organisation's `leave_paradigm` alone** — org-level `supports?` running before `HrPy::Au/Nz` serves an AU/NZ AIO member with payslips from `FetchHrDetails`, where `forecasted_accrual` stays nil; the OpenAPI `projected_leave_data` caller does `.to_f`, so a public `available_balance` silently becomes 0.0 with no error. Give each paradigm's balance fields one documented meaning: `HrPy::Base#current_balance = base - approved - pending` while HR Standalone returns `base_balance`, and where `projected_balance` already includes approved leave and `approved_balance` is also exposed, a consumer computing `projected - approved` double-deducts.
- **Compute pending and requested leave against the same `as_at_date` the balance is read at, and mirror the `access_leave_balance_improvement?` branch that v3 uses** — the v3 details path calls `GetLeaveDetails` with `target_date: as_at_date` when the improvement flag is on and passes its `total_units` as pending, while the v4 path always calls `GetLeaves` with the default `Date.current`, which filters yearly and per-pay-run categories to today's accrual year. A historical balance in another leave year therefore disagrees with v3, and the flag-off branch is the only one that matches.
- **Prove balance parity per balance-source cohort** — run the ledger-backed `access_uk_leave_balance?` branch and a multi-unit hours case against v3, and treat a column-presence run as no parity evidence. A spec that defines `access_hr_uk` as `false` and never overrides it leaves the UK/SG/MY/CA HR Standalone and AIO cohort — where `remaining_balance` and `pending_leave` come from `available_balance_data` and ledger-derived pending data rather than `accrued_amount` — uncompared; a run resolving no detail data (`non_nil=[]`) is a column-presence check. Comparing one hours request also misses a 5-day request with 3 `leave_hours` rows (v3 15.0, v4 5.0).
- **Bound a leave-year balance window on the transaction's `created_at`, never on the business-effective `target_timestamp`** — an `Adjust` transaction can be created before the previous year's `LeaveDetail` row exists, so filtering adjustments on `target_timestamp` pulls prior-year adjustments into the current year and carries a known bug in the old path.
- **Drive the backdated-transaction cutoff from a release-time configuration value (`EXCLUDE_BACKDATED_TX_RELEASE_TIME`) and open the removal change for the temporary `NOT EXISTS` guard in the same change** — a hardcoded cutoff date in `consts.rb` starts excluding backdated transactions on whatever date was typed, and the guard that exists only to survive the transition becomes permanent. Together they change which backdated adjustments count toward every year, silently.
- **Read a member's balance and the org's leave category list through the domain service that serves that organisation's payroll connection — `LeaveBalanceServices` for HR Standalone/AIOP and the HR+Payroll-connected balance service for payroll-connected orgs — instead of composing the balance inline** — each segment keeps its own balance source and each country its own pending and approved fetch (KP NZ uses a different class from KP UK), so a hand-written formula silently disagrees with the balance the product and payroll show. `LeaveBalanceServices::GetLeaveBalance` is HR Standalone/AIOP only and must not compute an HR+PY payout balance.
- **Convert a balance between days and hours using the member's own work-hours pattern, and state which employee populations the conversion is valid for instead of assuming standard full-time hours** — a leave payout is money, and a daily-hours constant is correct for full-time standard-hours employees and wrong for everyone on custom work hours. The conversion still returns a plausible number, so nothing fails visibly and the shortfall reaches payroll.
- **Serialise leave-balance sync per member with a PostgreSQL advisory lock keyed on a namespaced member string, and keep the payslip-balance delete and recreate inside the same transaction after the lock is acquired** — concurrent syncs for one member each insert their own balance rows, leaving duplicate pairs that double every downstream sum, and deleting before the lock lets a racing sync delete the rows the winner just wrote.
- **When a balance service's inputs or semantics change, enumerate every consuming surface and verify each by hand, not only through the service's own specs** — the same computed balance feeds leave-request create (`FetchHrDetails`), balance adjustment (`GetAvailableLeave`) and the leave-request management listing (`GetAvailableLeave`/`GetAvailableBalance`), and each surface has its own default as-at date and its own serialization of the result.
- **When a flag decides which balance is displayed, gate both the computed value and its extra metadata at the same boundary, and prove that flag-off renders exactly the pre-change `object.balance`** — gating only what reaches the serializer hands flag-off organisations a computed balance in place of the stored one, and an early return that skips computation for flag-off orgs is the only shape that restores the old behaviour. The test is parity of the displayed number, not the presence of a flag check.
- **Treat `eh_leave_balance_transactions.created_at` as a non-null ledger column: delete nil-safe guards and nil-defaulting display code instead of defending against a state the schema forbids** — a nil-guard on the ledger timestamp, or a `nil&.balance.to_f` that yields 0.0, renders a missing or unloaded transaction as a zero balance rather than raising, which in a running-balance series is a quietly wrong balance line. Likewise give the leave-balance self-invalidation predicate one shared definition across every balance read path and never copy it into a new balance query service: a duplicated `NOT EXISTS` block lives in the available-balance, balance-by-leaves, current-leave-year, historical-report and HR-query services, differing only by outer table alias, so a later change applied to four of the five silently makes reporting disagree with the live balance.
- **Short-circuit a balance transaction with no `log_leave_request_uuid` to "not superseded" before any per-member and per-category cache lookup** — caching the validity answer under `[member_id, leave_category_id, nil]` collapses every request-less transaction for that member and category into one entry, so the first transaction evaluated sets the answer for all later ones regardless of their own `created_at`, and one correction marks unrelated transactions superseded. The Ruby cache has to mirror the SQL side, where `NULL = NULL` is UNKNOWN and never self-invalidates.
- **Aggregate used units per unit type — `sum(leave_hours.hours)` for hours-type categories and `leave_requests.total_units` for every other type — and do not unify the two until `total_units` is proven equal to the hours sum against real data** — replacing both with one column silently changes every hours-type balance, so the split is intentional and the equality is unproven. Exercise the balance and edit-locking paths for each unit type separately (days, hours, weeks): a days-type category carries no leave details rows, so any lock or recompute keyed on those rows does not fire while the edit still succeeds.
- **When a balance read switches from the caller's balance to a `target_member` balance, test the global-teams org and state why `target_member` may be nil** — the endpoint returns a different person's balance after the change, global-teams orgs resolve members through a different hierarchy, and the nil case is where the endpoint silently falls back to the caller.
- **Verify a per-row classifier field's false case is reachable on every cohort the payload serves, and state the cohort scope in the field's own note** — each paradigm's candidate fetch decides which rows exist before the field is read: `HrStandalone::Base#fetch_leave_balances` calls `FetchList` with `hr_lb_accessible: true`, and `LeaveBalance.hr_visible` (`LeaveCategory.enabled.tracked.is_hr`) drops untracked and NULL `balance_untracked` categories, so for HR Standalone and AIO members the classifier is constant `true` and requesting such a category by id is a 404. Where a cohort cannot produce the false case, name that cohort and its source (there, the v3 `leave_summary/aio_leaves` call) rather than widening the candidate filter, because widening changes what the cohort sees.
- **Ship every leave-policy backfill with a dry-run mode, an explicit statement of what it does to rows that already have a leave-category setting, and a persisted record (CSV or log) of the categories it migrated** — a task that flips a per-category "prevent negative balance" flag across every org silently changes how much leave thousands of employees can book, with no preview and no way to name the affected set afterwards.
- **Cover the missing-settings-row case with its own spec and state the negative-balance defaults explicitly wherever a leave-category payload is built** — a nil that serializes as `prevent_negative_leave_balance: false` reads as prevention switched off for that category, so the spec compares both sources' serialized settings and asserts `prevent_negative_leave_balance || false` and `negative_leave_balance_prevention_mode || MODE_APPROVED_LEAVE_ONLY`.
- **Derive carry-over expiry from the carry-over transaction of the period being balanced, and return no expiry when that period has no carry-over transaction** — falling back to the most recent carry-over it can find makes the balance display an expiry already in the past: no carry-over for the period being balanced, an older period's 5-day carry-over, forfeiture three months later, and the live balance renders as expired. Resolve a forfeiture date from both the policy-fixed date and the member-based date, and treat a date helper that only supports the fixed mode as incomplete, as `LeavePolicyServices::DateUtils` was: a member-based policy routed through it forfeits on the policy date instead of the member's own.
- **Let the unique index and its rescue guard the duplicate forfeiture or carry-over transaction, instead of an existence pre-check that a concurrent scheduler or manual run can race past** — a check-then-create reads as safe because the forfeiture runs look serial, but overlap lets both pass the check and the member receives carry-over twice. The constraint is the contract and the pre-check is noise.
- **Scale carry-over by FTE only when the policy sets `carryover_based_on_fte` or `carryover_based_on_fte_days`; a standard policy must never call `member_fte` or surface a missing-FTE error** — an unguarded lookup makes standard non-FTE policies raise `missing_fte_error` during carry-over on data they never needed. The cap arithmetic is FTE-scaled only on the FTE paths (old 5.0, simulated 3.0, refund 3.0, adjustment 2.0 at FTE 1.0), which is what the spec asserts.
- **Compute the carry-over amount in one place that accrual, the balance serializer and backdated correction all call, and apply FTE scaling in every branch, including unlimited carry-over** — each caller keeping its own copy is how the unlimited carry-over case came to skip FTE scaling, so a part-time member is shown a carry-over that does not match the balance it derives from, and backdated correction clones the divergence.
- **Apply the negative-balance validation to every leave-request write path — create, update, approve and reject — not only the create service** — a guard that runs only on create is bypassed by editing a request to cover more days or by an approval path that writes the request again, and the org still ends up negative.
- **Treat request-level balance exclusion as a gated behaviour, not a property of the parameter**: `GetLeaveDetails#exclude_leave_request?` returns false unless `HrStandalone::LeaveBalancePolicy#correct_backdated_leave_balance?` (`access? && feature_flag_on?(:correct_backdated_leave_balance)`) is true, so a client that starts sending `leave_request_id` changes nothing for an organisation without that flag. Measured on live pending requests, the total stayed identical with and without the id on two flagged-off organisations and moved 4.0 to 3.0 on the one flagged-on organisation, so any verification plan for a "stop counting the request's own hours" fix must name an organisation whose gate is on. `FetchHrDetails` accepts `leave_request_id` and never reads it; the exclusion happens in the endpoint's `excluded_leave_request_ids` argument to `GetLeaveDetails`.
- **Reproduce a pending-leave double count only under `approved_and_pending_leave`** — with `approved_leave_only` the pending query (`leave_requests.approved IS NULL`) contributes nothing, so the request's own hours are never in the balance. The mode lives on `LeaveCategorySetting#negative_leave_balance_prevention_mode`, so a test org needs that mode as well as `prevent_negative_leave_balance`, and a category whose balance floors at zero.
- **Test a negative-balance guard as a role × org-type × approval-state matrix, including at least one org with the prevention feature switched off** — an org with the feature off must keep its old behaviour, and HR+PY, AIOP and employee-role accounts exercise different services behind the same endpoint.
- **In a leave approval-correction service, treat a unique-constraint violation on the correction row as the expected outcome: rescue `ActiveRecord::RecordNotUnique` and log it, without a pre-flight uniqueness check and without a hand-rolled retry for `ActiveRecord::Deadlocked` it caused** — the deadlock traces to the duplicate insert, so the constraint is doing its job and a retry loop only multiplies work.
- **Reject a non-finite or out-of-range `accrued_amount` at the API boundary before it reaches `leave_balances` or the ledger, bounding the magnitude as well as rejecting NaN and Infinity** — Oj parses `1e999` as `Infinity`, which is written to the float column `leave_balances.accrued_amount` and becomes the ledger delta, so one bad row in a 30-record batch corrupts a member's balance, and a later `finite?` guard still accepts `1e300`. Batch the balance reads for those members through the bulk `GetAvailableBalance` and bound the write transaction's lock window instead of looping one adjustment per employee in one request: a 30-employee UK/SG/MY/CA batch runs three leave-data calls (one a ledger query), an `edit?` check and a Keypay push per record and holds `leave_balances` row locks until the batch ends, while a query-count spec that stubs the service measures none of it.
- **In a leave-balance duplicate cleanup, prefer any record that matches the authoritative payroll balance and pick the latest among the matching records only, and normalise a nil report `unit_type` to the balance's default unit before comparing** — with three duplicates where two equal the active `LeaveBalance` and the newest differs, `matching.one?` is false, so the newest wins on `updated_at` and the two rows that agree with KeyPay are deleted. KSS writes `item.unit_type&.value`, and a report column with no default never matches `"Hours"`, so the match-first rule silently degrades to keep-latest and the balance that agrees with payroll is deleted. Bump the task version whenever a resumable repair task starts reading a new receipt column: when `RECEIPT_HEADERS` gained `keep_id` and `keep_basis` without a `TASK_VERSION` bump, `receipt.fetch("keep_id")` raises `KeyError` after `restore_rows` has committed, so every rerun dies the same way.
- **Report a failed leave-request rejection as an accumulated service error (`add_error`) that reaches the operator terminating the member, not as an error-tracker event, and choose sync over a worker whenever the operator must see that failure** — a rejection that returns `success? false` and is ignored leaves the member terminated with live leave requests and an unreverted balance, and deferring the cascade to a worker removes the only surface that could have shown the failure.
- **Read a balance through the canonical calculator (`GetAvailableBalance`) whenever a correction, export or reconciliation needs the number, never by summing or reading balance columns directly** — a hand-rolled read disagrees with the calculator once accrual, carry-over, forfeiture or pending requests are in play, so a correction built on it writes a wrong balance with no visible divergence.
- **Write a correction as a new leave-balance transaction whose `transaction_type` names the business cause and is reusable for future occurrences, committed in the same transaction as the balance change; do not reuse an adjustment service that requires a linked leave detail the correction does not have** — reusing the request-adjustment path with `leave_detail_id: nil` produces a transaction no reconciliation query can identify, and a one-off type per incident cannot be aggregated later.
- **Scope a bulk balance correction to balances whose organisation is eligible for `HrStandalone::LeaveBalancePolicy#access?` and whose members the org has not already adjusted by hand, and run it in fixed-size batches with a spot-check of the sampled data before writing** — payroll-connected orgs hold their balance in KeyPay, Myob or Xero rather than HR Leave, and orgs that already applied a manual adjustment get a second one; both leave a balance wrong and unwound only by knowing which rows were touched. Ship a backdated correction as a separate non-writing dry run beside the apply service, and prove the dry run writes no ledger transactions and that its predicted delta equals what apply produces, comparing transaction type and amount at a fixed scale (`pluck(:transaction_type, :amount)` rounded to 4dp).
- **Make every backdated leave correction self-invalidating by writing the pair's refund transaction so the backdated recompute cannot re-apply the corrected amount, and skip — never partially apply — any pair whose reconciliation does not pass** — a correction that only moves the balance lets the recompute apply the same change again, correcting the member twice, and applying a pair whose validation failed writes a balance nobody validated.
- **Key every leave-balance and leave-request lookup in correction and reporting code by the columns that scope it — `member_id` + `leave_category_id` for balances, `uuid` + `member_id` for requests — because those models carry no `organisation_id` to scope by** — a query missing those constraints can reach another member's balance and also fails to use the composite index. Organisation-id findings are not applicable to these tables for exactly that schema reason.

- **NULL FTE is an explicit error or review state, never a silent numeric fallback, and the frontend preview and the backend calculation must apply the same rule.** A backend that fell back to organisation hours while the preview computed differently disagreed silently for about 23 months across roughly 850 salary records, and no exception fired. Test both sides with NULL FTE input and assert they agree.
- **Validate the accrual-total units a payroll sync supplies before they feed a forecast.** Nil or zero passed straight through as the forecast input and rendered as a blank or zero forecast (WM-6249, CXP-19134); an explicit unavailable state is the correct output.

## Accrual and tenure

- **Wrap accrual and leave-balance specs in `travel_to` inside the timezone the accrual job actually executes in (the Sidekiq process zone, `Australia/Sydney`), and comment why that zone is used** — accrual runs on the Sidekiq process timezone rather than the application timezone, so a spec written in the default test zone stays green while production accrues against the wrong wall-clock date around midnight.
- **Handle the two accrual boundaries outside the normal comparison explicitly: a policy with `accrual_start` NULL, and a member whose `termination_date` equals `earliest_eligibility`** — both fall outside the window arithmetic: a NULL `accrual_start` makes the date comparison drop the policy's rows so the balance reads as zero, and on the eligibility boundary `get_current_tier` can return nil and `next_tier.id` raises, failing the post-termination update for exactly the members whose tenure just qualified.
- **Treat a missing FTE row for an accrual date as `nil` and handle it explicitly in the consuming accrual path rather than defaulting it to full time; when fanning out per organisation, derive the set with no valid FTE from `employees_by_organisation.values - fte_table.keys`** — a default FTE silently accrues at 1.0 for employees whose FTE is unknown or zero, over-crediting part-time and not-yet-onboarded members, and the value is indistinguishable from a real full-time record downstream.
- **Resolve the as-at date once in the balance service initializer (`as_at_day ||= Date.current`) and never let a nil as-at day reach accrual or tier arithmetic** — a nil as-at date forces every downstream lookup to invent its own "today" or compare against nil, so the same query returns different numbers by call path and day, and no spec catches it because each path defaults differently.
- **Treat accrual frequency and balance-reset cycle as independent settings — a monthly policy can still reset and carry once a year, so a monthly balance read must not be hardcoded to the current balance** — `fetch_hr_details` used the current balance for anything monthly, which is right only for policies that never reset.
- **Scope the existing carry-over and year-opening balance query by `leave_balance_ids` instead of adding a member-scoped variant class beside it, and when a leave service duplicates what the leave-management package already provides, write the reason it cannot reuse it into the file** — variant classes for one purpose are the class proliferation leave already carries, and duplicated balance paths drift. The only reason the new class could not be reused was that the existing latest carry-over and latest accrue lookups ignored `leave_balance_ids`.
- **Tie accrual-frequency documentation to the implementing code, citing the `leave_tier_utils.rb` line range and stating the per-frequency boundary differences rather than describing accrual periods from memory** — an `end_of_period` path that shifts the date `+1.day` and then compares with `>` where `start_of_period` uses `>=`, a `== 13` check that does not exist, and frequencies that only match through the yearly date logic when `accrual_day` and `accrual_month` are both present, send whoever debugs a missing accrual to the wrong condition.
- **Derive the current and next leave-year start from the member's accrual tier period and `member.start_date` (the `LeaveTierUtils` period helpers), and gate any change to that derivation per customer so an already-live customer keeps its existing boundary** — a leave year is a per-member anniversary or tier period, not a calendar year, so deriving the boundary from `Date.current` alone moves it for every member whose start date is not the calendar boundary, and changing the derivation under a live customer re-dates accrued and already-deducted balances. Compare a target date against a tier's accrual day through the clamped helper (`get_safe_date(year, month, tier.accrual_day)`), and when a tier period cannot be resolved return an explicit `[period_start, nil]` rather than a plausible end date or an empty array: a tier with `accrual_day: 31` raises or rolls over in a short month.
- **Resolve a prior-period boundary from the policy's leave-year definition in one named helper — `last_period_start_date`, matching `Accrual::LeaveTierUtils` — and test both sides of the boundary date rather than inferring the previous period from the calendar year** — a prior-year negative-balance gate that resolves the wrong period start either blocks a valid new-leave-year request or lets a negative prior-year balance through, and the boundary is only visible when the spec exercises the day before and the day after the leave-year start.
- **Resolve the accrual anchor before prorating or applying a backdated correction, because month and day are nil when accrual is anchored to the employee start date and the leave category type decides whether they are required at all** — a correction that assumes the anniversary month and day are populated reads nil for every start-date-anchored policy and applies against the wrong anniversary; OSL categories are where those fields are legitimately absent, so anchor and category type are resolved together.

- **Isolate accrual failures per organisation.** A sequential accrual run raised on a query timeout for one large employer and stopped processing every organisation after it: 8,474 organisations and 88,412 missing transactions. A single organisation's failure must not halt the run, and organisations skipped or errored need an alert with a named owner.
- **A shared date helper that can return nil must be nil-protected where a self-scheduling worker consumes it.** A nil date fed a worker that re-scheduled itself without terminating, produced more than eleven million jobs, and exhausted Redis, degrading Core HR, Payroll, Work App and the time clock for about four hours. Validate the input before re-scheduling, and load-test the fan-out of a self-scheduling worker.

## Requests and approvals

- **Filter, paginate and derive year membership of leave requests from `start_date`, never from `end_date` or `created_at`** — filtering across the domain keys on start_date, so a cursor or year calculation built on another column returns a different set than every other filter and produces balance histories that skip or repeat a request at the boundary.
- **Decide up front whether a leave-request endpoint serves the member themself or a manager acting on behalf, and place an on-behalf endpoint under `members/leave_requests` with the target member resolved through the subordinate scope; do not put an on-behalf target param on a self-service route** — resolving through `subordinate_scope` both authorizes the target and gives a 404 for an out-of-scope id, and inline re-derivation in the controller is where the redundant `peo_member` comparison appeared.
- **A leave-type suggestion API may only offer categories the target member can actually request, must reuse the existing requestable leave-categories service instead of a parallel list service, and returns a null suggestion when the proposed category falls outside that set** — a suggestion naming a category outside the member's requestable set turns a wrong suggestion into a failed request, and pushing the filtering to the client duplicates a rule the backend owns.
- **Censor leave-request free-text and category fields (reason, comment, sick_reason, leave_category_name, leave_category_id) for any viewer outside the permitted id set, and implement it as an includable serializer concern so a serializer that already inherits a base class can still adopt it** — leave requests carry health and personal reason text, and a serializer that exposes it to an unpermitted manager or peer leaks it in every endpoint that reuses the serializer. Censorship by subclassing does not work, because Ruby single inheritance means the first serializer with another base class cannot adopt it.
- **Model a leave-request API payload against every leave-category unit type (hours, days, weeks) and both leave paradigms (HR+PY and HR Standalone)** — the accepted shape differs per unit type and per paradigm rather than collapsing to one total: `hours` is an array of dates with hours per date, HR+PY takes a `total_units` number for days and weeks, and HR Standalone takes an array of dates with a unit count per date. The endpoint's schema is a per-tenant contract, not a global one.
- **Identify a leave category by its leave-category type, never by its leave reason, and guard the type check with `is_a?(LeaveCategory)` because a MYOB org's `leave_category` is a `PayCategory` that does not respond to `leave_category_type`** — leave reasons are shared between categories, so a reason-based branch fires for categories the feature was never built for, and the unguarded call raises NoMethodError on every MYOB submission. The shape is `return unless leave_category.is_a?(LeaveCategory) && leave_category.leave_category_type == LeaveCategory::LEAVE_OF_ABSENCE`.
- **Treat `requester != member` as insufficient to mean "admin-initiated" on a leave action; require the requester to be outside the requester-to-member management chain as well** — a manager is also "not the member", so an equality check alone routes a manager's own request through the admin-only branch that exists for HR acting on someone else's leave.
- **Keep a multi-level leave approval setting in the settings surface that owns it — the 2-level approval belongs to the advanced-settings tab — and publish a navigation-metadata entry only for a setting whose backend permission check also exists** — a metadata entry for a control that lives elsewhere makes the control appear twice and the obvious cleanup deletes the live one, and a menu entry without a backend gate advertises a control the API does not check.
- **Express the two-level approval threshold as an explicit approvement-count comparison derived from the configured level count, and assert the boundary at the configured value** — a generated predicate that collapses to `lra_counts.approvement_count BETWEEN 1 AND 1` for a two-level setting treats a request as fully approved at one approvement, which is invisible in a diff that only changes the query builder.
- **When a member terminates, cancel only unprocessed leave requests that are not already synced to payroll, and leave a request whose `start_date` equals the termination date in place** — cancelling a processed or payroll-synced request reverses a deduction payroll already paid out, and cancelling the request starting on the termination date removes the member's last valid leave day. Attribute the termination-driven cancellation to an active organisation admin or owner resolved at execution time, after verifying what `termination_info['current_membership_id']` stores: an actor resolved from the wrong id records the cancellation against the member being terminated, so the audit trail names the victim and the notification goes to the wrong mailbox.
- **Keep the leave-request-manager recipient resolution unchanged when touching preloading — direct primary and secondary managers with the fallback to indirect primary managers — and prove an ordering-preserving preload before replacing it** — who receives a leave-request email is who can act on the approval; dropping the indirect-manager fallback leaves requests with no recipient, and an `includes`/`eager_load` rewrite loses the association order so the email goes to a different manager.
- **Model a leave request as owning many leave spells, and carry every unit field the single-request create accepts (`leave_days`, `leave_hours`, `leave_weeks`) into each part of a split request** — a `has_one` spell assumption makes a split unrepresentable, and a part-builder that copies only days and hours drops a weeks-unit request's weeks, so the parts no longer add up and no validation fires.
- **Reject a leave request whose total units resolve to zero unless it is an open-ended request satisfying the open-ended conditions, and express that as one condition on the units rather than a compound of persisted and changed flags** — a zero-unit request creates an approved record that deducts nothing but occupies its date range, so overlap checks, availability and approval counts treat the member as on leave. The `!(persisted? && !total_units_changed?)` guard both admitted the wrong edits and was why the spec failed.
- **Validate leave overlap against the member's approved-or-pending requests across other leave categories, deriving every hours, days and weeks sub-query from that member-scoped relation (via the `auth_context` requester and member pair) rather than querying the unit tables directly** — an overlap check confined to one category approves annual leave on top of approved personal leave for the same day and deducts the member twice, and a direct `LeaveHour`/`LeaveDay`/`LeaveWeek` query loses the authorization scope the policy needs. `auth_context` carries requester and member for `LeaveRequestManagementPolicy.use?`.
- **Validate partial-day time ranges on `LeaveRequest` itself, applying the rule whenever `start_time` or `end_time` is supplied — regardless of the `use_leave_requests_half_day?` setting — and require both ends before treating the request as a timed partial day** — a full-date request can still carry explicit times, so gating on the half-day flag or checking only `start_time` lets an end-time-only or inverted range through and the duration computes to a negative or full day. Holding the rule in a bulk-create concern hides it from every other create path.
- **When a termination-driven leave cancellation cannot resolve its hr admin, record a translated, non-technical error and fail that cancellation instead of skipping the request** — a skipped request stays approved after the member is terminated, so the balance stays deducted and the termination completes looking clean, while raw exception text hands the employee an internal message they cannot act on. Pass an explicit skip flag from the termination path instead of weakening the leave mailer's inactive-member guard for every caller: disabling it re-enables every send path to departed members.
- **Cancel leave on termination in one transaction that declines pending and approved-but-unsynced requests, writes the decline audit trails inside that transaction, and defers notifications to after-commit** — an approved request that never reached payroll still deducts leave for a member who has left, an audit trail written outside the transaction can fail after the declines commit, and a notification sent before commit can announce a cancellation that rolls back. On every termination path, including a re-termination that updates final entitlements, cancel open leave requests and refund the balance beyond the termination date, with the ordering enforced inside the refund or termination method rather than by call-site line order: re-nesting `cancel_leave_requests if success?` inside a branch stops it running on the entitlement-update path, so a terminated member keeps approved future leave that nothing consumes or cancels.
- **Raise the member cap on bulk leave-request creation only after the batch throttle is released and production evidence exists for Redis key and Kafka message volume, an all-batches-fail run, and a multi-org stress test at the new cap; never lift the maximum-days span cap on a single leave request** — a request spanning 279 years previously took Redis down, and the days cap is the standing protection while the member cap multiplies concurrent keys and messages.
- **Convert an existing leave request to hours for a cross-category overlap check from that request's own `total_units`, never from the request under validation, and read the work-day pattern through `member.get_typical_work_day` rather than the raw attribute** — using the new request's units makes the per-date hours wrong whenever the two requests differ in duration or category, so an overlapping second request is accepted or wrongly rejected, and reading the attribute bypasses the override the tests stub.
- **Define who can approve a leave request once and consume that one predicate in every submission form, including the AIO add-leave footer and the bulk create form** — two independent `show approve` condition sets in one leave flow mean one form offers approve where the other does not, and every later change to the rule has to be found in both.
- **Treat `leave_requests` as closed to new columns: put the roster-shift link, and any further leave-request attribute family, in its own `leave_request_rostered_shifts`-style table** — `leave_requests` is capped by policy (CTD-764), so one nullable foreign key still widens the busiest leave table and becomes the precedent for the next one, which the general 25-column gate would admit as a single one-off column.
- **Keep an absent leave linkage nil: never `to_s`, `to_i`, or substitute a fallback when a migrated record has no EH leave request or no external id** — `nil.to_s` yields `""` and `nil.to_i` yields `0`, so a link that legitimately does not exist becomes a value that joins, matches or sorts as the first record. A `""` leave_request_uuid and a zero external id both read downstream as real identifiers.
- **Run the real-time Kafka leave-request flow in parallel with the batch `processed_leave_request` flow, excluding records the new flow already processed, before retiring the batch path; confirm first that the new flow handles open-ended leave requests** — the batch path is the only handler that can reopen an open-ended request and its `.update` reassigns processed state, so a one-release cutover loses the open-ended case and overwrites work the Kafka flow completed.
- **Run a leave-request import under one job-level lock per batch, with approval history preloaded and each request's status reloaded, rather than `with_lock` per row** — row-exclusive locks turn a batch into hundreds of lock round-trips on the table live approvals are writing, the per-row iteration re-queries approvals and declinements, and the row-wise path risks a notification storm on live requests.

- **Evaluate auto-approval on an edit against the updater, not the creator** — a manager-created request that the employee then edits must re-enter the workflow; checking the creator identity (still an admin or manager) auto-approves it again with no review. The creator check shipped and went undetected for four months, leaving roughly 1,700 requests mis-approved across two cohorts.
- **A comment save is not a content edit.** Treating a manager's note on a pending request as an edit makes the manager the updater and puts them on the approver list, so auto-approval fires without an Approve click; that shipped as a follow-on to the updater fix and touched 2,618 requests. Separate the two write paths, and after any change to who counts as the actor, test every updater type: employee edit, manager comment, admin action.
- **When approval logic moves between layers, carry every condition the old path evaluated elsewhere.** A Workflow Engine branch written as `admin/owner && restrict_admin_overrides = false` reproduced proxy submit and admin-without-manager but dropped the manager-presence dimension, so an admin with a manager self-submitting was auto-approved instead of routed to that manager: 2,858 requests across 1,557 organisations.
- **Admin self-submit with a manager routes to the manager; it does not auto-approve.** Test the actor matrix by name: proxy submit, admin self-submit without a manager, admin self-submit with a manager, admin self-submit with a manager under `restrict_admin_overrides`, manager self-submit with their own manager, and a security-group-granted member. The role × paradigm matrix alone does not cover this.
- **Any change to `restrict_admin_overrides` or `wfe_restrict_admin_override_leave` tests force-approval, a single approver, several approvers, admin and owner self-submit, and manager present and absent.** An over-broad condition blocked force-approval and turned fully approved requests into partially approved ones for single-approver organisations (WM-6020, CXP-17304, CXP-17696).
- **Approval, the balance deduction, and the history write belong in one transaction.** Without a wrapping transaction a failed deduction leaves the request approved with an unchanged balance and no history row (BOBA-124, CXP-18929). Test the state after a deduction failure.
- **Legacy and admin-created requests that later enter the approval path need end-to-end coverage**, including a proxy submission that re-enters the workflow. Regressions here reach customers before a test does.
- **Every serializer field that includes related data carries its own authorization check, and staging data includes representative attachments.** A serializer exposed attachment data with no check, and staging held no attachments, so the exposure surfaced in production as a severity-one privacy incident.

## Categories and policies

- **Compute leave calendar years, latest start dates and every other leave aggregate from the same CSS-scoped leave-request relation the list endpoint uses** — a `maximum(:start_date)` over all requests returns a year no visible request belongs to and tells the member that a request they may not see exists. An aggregate helper that returns a date rather than a record reads as a date-picker utility and escapes the scoping review.
- **Ship the removal of beta public-holiday templates from a calendar's `/templates` list only after the frontend that reads `template_public_holiday_calendar` is live, or keep returning the linked beta template until it ships** — `EditCalendar` looks the linked template up in the `/templates` list, so a beta-linked calendar gets `[]` and `enabled_public_holiday_ids` is empty, while `UpdateService#existing_settings_attributes` writes only ids that appear in the enabled or disabled set: a re-enabled public holiday is never applied and the update reports success.
- **Serialize blackout periods with only the fields the calendar renders, and never return the whole leave category record from a blackout-period serializer** — a payload built from the category serializer exposes leave-category configuration the team calendar does not need to anyone who can read the calendar.
- **Create default and system leave categories at organisation creation (country defaults) plus a one-off backfill for existing organisations, and never provision them lazily inside a read or GET path** — lazy loading makes a GET leave-categories endpoint write rows as a side effect, has to be repeated at every entry point that lists categories, and leaves a second provisioning path beside the org-creation seed that can drift. Make system-owned creation tolerate pre-existing manual rows: match on `created_by_system` and treat a name clash with a manually created category as a resolvable conflict, never a failed creation, or an org that already has a hand-made LOA category ends up without the system category the rest of the feature keys on.
- **Skip the generic organisation-level default leave types when the organisation's country already supplies statutory default leave types, and map statutory time-off to the country's LEAVE entitlement rather than a new entitlement constant** — the org-creation seeding path is reached for every country, so an org can end up with two competing default sets and the wrong entitlement on statutory categories; the test is literally "will also be executed if the organization is CA".
- **Put new leave-policy settings on a feature-scoped child table keyed to the policy (the `eh_leave_policy_fte_settings` pattern — here `eh_leave_policy_accrual_settings` or `eh_leave_fixed_term_contract_policy_settings`), never as another column on `eh_leave_policies` and never in a general-purpose `eh_leave_policy_settings` bucket** — `eh_leave_policies` is already past its column budget at more than 25 columns, and a general settings table has no natural ceiling while a feature-scoped table is bounded by the feature. Treat `leave_requests` and `eh_leave_policies` as frozen at their cap: a new leave attribute goes into a new concept-named table such as `eh_leave_fixed_term_contract_policies`.
- **Leave-category updates exposed to HR+PY organisations must write through an explicit allowlist of updatable attributes, not by forwarding the API's permitted-params hash into the update service** — passing the API-allowed set through means any later widening of the public API silently widens what the payroll-connected path can write, including attributes that branch must not touch.
- **Gate an in-development leave feature with two independent checks — an early return when the feature is not enabled, plus the leave-domain policy or access check — so the code path cannot activate in production through either gate alone** — a sub-feature reaches production as soon as its create path is wired in, and a flag alone does not cover the org's leave-policy access, so an org that never opted into the leave type still gets the behaviour.
- **Name the parity target of a v4 leave-settings port — the v3 implementation or the written policy — and where v3 behaviour is a known bug, fix it in the port or record the deferral with a ticket instead of copying it as parity** — with no named target, "copies v3" and "matches the doc" become interchangeable defences for whatever behaviour the code already has.
- **Label an id-and-`enabled` comparison of a v4 leave-settings index as weaker than field-level parity, and state in the verification report which branches the run did not exercise — draft rows, restricted callers, a removed publish path — instead of letting a green count imply them** — a reader of the checklist alone otherwise concludes the port was fully verified, and the removed `destroy` bus event and employee and CSS callers go untested. Bound this work by category count: batch the per-row lookups, paginate before computing, and assert a query-count budget that does not grow with the number of categories. Each category running its own `FetchHrDetails` (category lookup, `find_by` per rounded value, tier and policy queries, carry-over and expiry queries) with `item_per_page=1` still costs N categories, and a `count_queries` helper used only for `supports?` measures none of it; the accepted shape resolves `deletable` for the whole page in two queries, with a spec asserting two queries whatever the category count.
- **Derive a row's tracked flag from `LeaveCategory#tracked?` (`balance_untracked == false`) and read a persisted `null` as untracked; the `!balance_untracked` form in the row serializers answers a different question** — the partition is `balance_untracked IS FALSE` for tracked and `IS NOT FALSE` (NULL included) for untracked (`LeaveCategory.tracked`, `get_non_tracked_leave_summary.rb`, `get_py_connected_tracked_leaves.rb` filtering `balance_untracked: false`), while the `!leave_category.balance_untracked` occurrences in `hr_leave_balance_serializer.rb` gate occupational-category adjustability, so copying that form reclassifies every legacy NULL category as tracked. Read a draft leave category's `balance_untracked` of `null` as "not answered yet", keep it `null` through contract, mapper and UI, and never coerce it to `false`: an unlinked draft carries the value from the wizard's `draft_data`, and a contract typed `boolean`, a draft fixture set to `false`, and a pass-through mapper make it falsy downstream, where `getPolicySettings` reads falsy as tracked, so an unanswered draft renders as a policy decision.
- **Treat an explicitly null leave-category setting as not sent when deciding which fields an update refuses, matching the legacy service's null-skipping, and keep counting only the fields the legacy service writes** — a v4 PATCH that refuses `{require_note: nil, sensitive: nil}` with 422 where the live PUT returned 200 blocks a client round-tripping a form with untouched gates, while `name` and `color_code` must still count because the legacy service writes them as sent.
- **Return every leave-category field the create or update accepts from the same API, or declare it write-only in the apib — never accept and persist a field the v4 row and index never emit** — `blackout_period_exempt` is accepted and persisted but absent from `LeaveCategoryItem`, the serializer and the index, where v2 echoed it, so an HR Only admin with the blackout gate on cannot read the saved value back or tell whether the exemption in force, and the request spec never asserts it persisted.
- **Check `success?` on a leave category loader result before calling `row`, and render the loader's errors instead of dereferencing a nil result** — on dry-monads 1.3.5 `Failure('boom').success` returns nil, so an unguarded `item.row` raises after the write has committed, and the route must answer 422 with the loader errors.
- **Block deletion of a leave category that is a system-created statutory type — `AIO_STATUTORY_LEAVE_TYPES.include?(record.leave_category_type) && record.created_by_system` — and evaluate that policy per leave-category record** — a statutory category carries a legally required entitlement, so deleting it removes the entitlement and orphans the balances, requests and policy rows that reference it. Passing the category as the policy `record` is the shape to prefer.
- **Verify a leave-policy change under every leave feature flag that reaches the same code path — `core_leave_engine` and `leave_requests` — and state the release order when only one flag was tested** — the policy class is reachable under both, so testing under `core_leave_engine` alone ships the change to the population gated by `leave_requests` with no coverage.
- **Gate a new sensitive leave-category field with its own manage-level predicate that embeds the `sensitive_leave` feature flag and the HR Leave balance-policy `manage?` check, rather than reusing the read or expose permission or trusting each endpoint to add the entitlement check** — reusing `access_sensitive_leave` denies the write to any admin lacking that CSS, and a flag-only predicate authorizes a caller that never checked the balance policy. Putting `HrStandalone::LeaveBalancePolicy.new(auth_context).manage?` inside the policy method is what makes the check survive a second API or service calling the same policy.
- **Check a new leave-balance open-API policy against how the other `open_api` policies authorize before merge, and confirm with the owning squad when the pattern is unclear — a plan or entitlement check on its own under-authorizes** — an endpoint gated only on the organisation using HR Leave stays reachable for users who should not see balances.
- **Enumerate the leave-year schemes the code must serve and handle the CA non-yearly scheme explicitly; a path that assumes a yearly leave year must fail visibly rather than compute or correct a balance for a non-yearly member** — leave-year-dependent logic built for yearly periods mis-corrects or silently skips those members, and the same gap surfaces again in the leave-year-start helper.
- **Gate FTE and other balance-derived serializer fields behind the leave-section flag and return nil when it is off, and send a bug report rather than returning nil when the flag is on and the data is unexpectedly missing** — a new balance field added beside an existing gated one ships data while the leave section is hidden, and a silent nil for data that should exist is indistinguishable from a member with no balance; add the flag check at both the endpoint and the serializer.
- **Prove from the data and validations that every balance row has a non-blank policy name, then delete the branch that returns nil for a blank one instead of defending against a state the data forbids** — a defensive nil makes a real data defect render as an empty policy on the balance screen, which nobody investigates. Verify first; do not delete blindly.
- **Key a leave feature that is converging across org types on the concept name, and do not introduce or keep an `aio_` or org-type prefix in new keys** — a prefixed key duplicates the concept and freezes the org-type split into every call site that later has to be undone.

- **Filter `enabled` in every query that lists or evaluates leave categories.** The workflow condition query did not, so disabled categories appeared as selectable workflow conditions (BOBA-125, CXP-18810); a query that deliberately includes them says so.
- **Filter both `enabled` and `assigned` on every surface that lists categories.** The balance widget and other surfaces have shown disabled or unassigned categories (CXP-12751/SEN2-507), so the filter belongs in the query that serves the surface, not in each consumer.
- **A permission check proves enablement and scope, not enablement alone.** The leave-reason API checked that the permission was enabled but never that the caller's CSS scope permitted the data, exposing leave reasons across 76 organisations and 256 users. Add the CSS-scope cases for any API that gates leave-data visibility.

## Payroll synchronisation

- **Apply leave-category visibility rules (hiding `is_hr` categories from HR+PY organisations without AIO leave access) inside the query service keyed on the org's capability, and keep that filter out of the public API's parameter surface** — an `is_hr` query param makes the exclusion the caller's responsibility and lets a client opt back into categories the org must not see; derive it from `payroll_connected? && !aio_leave_access?` so every caller gets the same rule.
- **Resolve payroll identity and leave-category scope through the payroll-paradigm-aware path — `payroll_info`-scoped predicates and `HrStandalone::LeaveBalancePolicy#access` over `organisation.leave_categories` — not org-level predicates like `organisation.myob?`** — in a multi-payroll org `organisation.myob?` and `payroll_info.myob?` are different answers, and HR-standalone categories carry no `payroll_info_id`, so the only correct read is the leave policy's access check plus the org's own leave categories.
- **State the supported org and paradigm matrix for a leave-balance feature before release and take unsupported segments to product explicitly, instead of encoding a guessed gate and shipping silently without them** — a release that turned out not to cover PEO employees excluded a customer segment nobody had asked product about, and the gate encoding the assumption is discovered by the customer.
- **When porting a leave operation into a per-paradigm class, reproduce that paradigm's own authorization from the source API and cite the original lines, instead of copying another paradigm's check or dropping one the source API applied** — the delete-leave-category paradigms authorize differently: HR-Only applies no extra permission, HR Standalone applies one, and AIO requires two (`leave_categories.rb#L406-L408`), so a ported class either invents a check its paradigm never had or loses one it did, and the route gate substitutes only for the predicates it performs.
- **Describe a leave capability's paradigm scope exactly — "all org paradigms" when every paradigm receives it, and "not open" only when the paradigm table actually closes it — because that string is read as the capability contract by the next gate, policy or rollout** — an annotation saying "AIO orgs" when the predicate applies to all paradigms, or a table comment saying balance tracking and unit type cannot be opened when they can, produces a wrong gate rather than a runtime error.
- **Keep every `require_*_migration_off!` routing guard when a leave-settings path is ported into the per-paradigm services — the guard, not the paradigm class, refuses the mutation for an organisation still on the legacy leave-settings or payroll flow** — dropping the guards while decomposing the handler into AIO, HR Only and HR+PY classes lets the new path delete a category whose leave data is still owned by the v3 flow.
- **Scope each leave-category rule to its paradigm: statutory-leave deletion blocking and leave-request or balance usage are AIO rules, HR categories keep the V2 rule of no leave requests and no balances, and HR+PY payroll-owned categories expose no enable, disable, delete or visibility action** — applying an AIO rule to HR categories blocks or deletes the wrong set, and giving an HR category leave-request affordances allows requests against a category that cannot carry balances.
- **Add a new leave-settings permission key to both `leave_category_services/get_permissions.rb` and `hr_standalone/leave_category_services/get_permissions.rb` in the same change, because the v4 permissions response reads one of them for AIO and non-AIO orgs alike** — a key added to only one is absent for the other org type, so the capability is invisible to exactly the tenants the consolidation targets.
- **Pass the HR and AIO visibility flags into the category fetch behind a balance list, so disabled, balance-untracked and `is_hr: false` payroll-owned categories never appear as balance rows** — `Paradigms::Base#fetch_leave_balances` calls `FetchList` with no `hr_lb_accessible`/`aio_lb_accessible`, so the `hr_visible` scope (`enabled.tracked.is_hr`) is not applied and those categories leak into a balance list while `not_private` silently drops private ones. Cover it with a payroll-connected AIO fixture and a `hide_balance`/`is_hr: false`/`enable: false` spec.
- **Build the policies behind a balance view from the requesting member's auth context, and thread `current_member` through the paradigm factory instead of letting it default to the member being viewed** — `FetchHrDetails` defaults `current_member` to `member` while v3 passes `current_membership`, so an admin viewing a subordinate is filtered as the subordinate (`ListLeaveCategories` probation filtering, `LeaveRequestWithDaysOrWeeksPolicy`, `HrStandalone::LeaveBalancePolicy`), and `Organisation#leave_balance_policy` builds an org-only `AuthContext` while `worker_type_access?` returns true when the member is nil.
- **Keep authorization at the route for a migrated leave-settings surface, and in the shared service or paradigm record which gates each caller must own instead of repeating the check or internalising a migration-off gate** — paradigms and the extracted create service deliberately carry no permission check of their own, and moving v3's `require_leave_settings_migration_off!` or `require_sea_leave_settings_migration_off!` into a shared service would 403 exactly the migrated orgs v4 exists to serve. Accept that shape only with evidence of caller equivalence — a table showing V3 and V4 admit the same callers despite the missing `css_leave_settings_management` flag check — plus a note on `#call` that callers must enforce equivalent gates.
- **Model the v4 leave-category index draft rows as nullable (`id`, `uuid`, `payroll_settings`, `usage`, `settings.balance_untracked`) in client types, mappers and fixtures, and keep fixtures on the current contract** — standalone wizard drafts come back as `id: null, uuid: null, payroll_settings: null, usage: null`, so non-null types and a fixture that is a linked draft with every field populated let `toV3LeaveSetting` dereference `usage` and raise once the hook is wired. A fixture still listing `state`, `source` and `provider` after they were removed is stale in the other direction.
- **Gate leave-settings writes on the route gate and `leave_settings_management_granted?`, and delete paradigm-level `manage_leave_types_and_policies?` checks because that predicate admits managers** — `manage_leave_types_and_policies?` is `manage? || manage_via_css_leave_types?`, so it lets managers through an endpoint managers cannot access, while `manage_via_css_leave_types?` requires `css_leave_settings_management`, which is on only for UK. Refuse a paradigm-declined write with 422 and a documented `reason`, resolving a payroll-managed category to `availability_managed_in_payroll` or `create_managed_in_payroll` before any lookup or write, and keep 403 for the route gate alone: a lookup-first path answers 404 where v3 answered 403 from a `before` block, and the apib must be updated with the port.
- **Resolve `payroll_info_id` org-scoped at the API boundary with `PayrollProfileHelper`, for HR Only only, pass the resolved profile downstream as `options[:payroll_info]`, and assert the persisted id** — `PayrollProfile#find_resources` filters `where(payroll_info_id: id)`, so a create that drops the id, whether by declared params stripping it or the paradigm hard-coding `payroll_info: nil`, persists NULL and the category never appears in the profile-scoped list where v2 persisted it. Resolving the profile in a paradigm also skips the ownership check, and resolving it for every paradigm turns a stale AIO `payroll_info_id` into a 404 v3 never returned.
- **Require `accrual_type` whenever `balance_untracked` is false in every create port for a leave category, and keep that as a 400 in the new paradigm** — v3's conditional `requires :accrual_type` under `given balance_untracked: ->(val) { val == false }` is the only thing stopping a tracked category being created with no accrual type, so dropping it in the v4 route leaves the accrual behaviour of a tracked category undefined; carry it as `accrual_type_required` in the AIO paradigm.
- **Thread the route's `auth_context` into every leave-settings service, factory and paradigm, and stop rebuilding an `AuthContext` from `current_membership`** — a rebuild can diverge from the route's resolution, so the paradigm's org check and the auditor id come from a different identity than the gate that authorised the call. Report paradigm refusals through `ServiceBase#add_error` with a typed error carrying a code, and keep the response `reason` inside the set the apib documents: a bespoke `Error` class with a `Result` struct and a status-to-HTTP map duplicates the service base and lets gateway codes such as `duplicate_leave_category_name` and `leave_category_not_found` leak into `reason`, while a plain String surfaces as `reason: "StandardError"`.
- **Produce a leave category's row for the single-item loader and the index from the same paradigm-supplied data, and assert row parity in a spec rather than assuming the two paths agree** — an HR Only organisation can have the index attach `setup_wizard` where the loading paradigm returns none, so one category serialises differently by route. The durable shape is the paradigm returning `setup_wizards` on its result and the loader passing it through, not `SerializerOptions items:`.
- **Gate a new leave-domain validation or payroll-sync behaviour behind a feature flag in the in-house flag service from the first change, so the flow can be disabled without a code revert** — leave validation changes ship into the approval path of every org in the region, and reverting them means another deploy of the same path.
- **Route leave-domain authorization through the existing leave policy objects (`HrStandalone::LeaveBalancePolicy#access`, `LeaveRequestPolicy`) instead of an inline org-type or entitlement condition** — the policy already encodes the org-type matrix the domain supports, so an inline check is a second, drifting copy that grants or denies a different population and hides which org types the endpoint actually serves.

- **A leave deleted before its external payroll id arrives cannot dispatch a deletion, and must not be dropped silently.** The deletion event has no id to send, so it disappears: confirm the external id exists before dispatching, and otherwise enqueue a retry or flag the row for reconciliation (WM-6009, CXP-17419; confirmed for KeyPay, unconfirmed for Xero and MYOB). Test deleting a request immediately after creation, before the asynchronous id callback.
- **For a NZ KeyPay balance import, exclude forward-dated entitlement.** The provider can send a balance that includes a period before the member's anniversary, so HR displays an inflated balance (NP-1237, CXP-11313). Read the payroll-sync contract before changing the NZ import.
- **Any change to Xero leave-category sync tests initial sync, re-sync, organisation reconnect, and a category rename.** Duplicate categories appear for Xero organisations and the root cause is unconfirmed (CXP-16559, CXP-16673, CXP-16773), so the pattern is only guarded by coverage.
- **Check `processed?` or `partially_processed?` before editing, cancelling, or deleting a leave request in an AIO KeyPay organisation.** A request locked to a pay run through `processed_info` must not be mutated, and the `DuplicatePayRunError` and `PayRunNotExistError` guards in the sub-processors stay. A UK Kafka consumer change also needs CA verification, because both countries share the code path.
- **A change to request state, pay-run finalisation, or balance-update triggers must exercise the finalised-pay-run path.** Leave requests failing to lock and balances failing to update after a finalised KeyPay run is a recurring report (CXP-15308/SEN2-1901, PRD-7993), and it is invisible to a test that never finalises a run.

## Reporting and exports

- **Gate leave-report access on the entitlement first and fall back to the feature flag, and do not add new sub-plans to the `reports` feature-flag list** — a flag used as the plan gate forces a new sub-plan either into the flag list or out of the report, and entitlement-first keeps plan entitlement authoritative with the flag as a release control. A policy that checks `all_employees` management scope is not the report-access gate.
- **Prove a legacy leave report or list payload is unchanged with a before/after capture of the same requests, rather than inferring it from the serializer's field selection** — a name-picking serializer is a good argument but not evidence; capture the response bodies either side of the deploy and compare every field with no keys ignored, because a leaked key changes a customer-facing report silently.
- **Check a before/after sandbox diff of leave-settings payloads for data drift — a leave-category rename or an `attachment_requirement` edit between captures — before attributing the difference to the change, and say when that cause is unproven** — leave categories are freely edited rows, so a capture proves nothing about code unless the dataset is shown stable or the drift is named.
- **Authorize a leave report's category list through the shared `hr_standalone/leave_balance_policy` that covers both HR Standalone and AIOP, not a surface-specific permission check** — a narrower check per surface means the same viewer sees different leave categories depending on which product surface rendered the report, and fixing one surface while deferring the other is how the divergence survives.
- **Keep retrospective leave requests that fall inside an already-finalized pay period in the external-payroll export, and make any exclusion a payroll-admin configuration rather than a silent filter** — dropping a request that arrives after its pay run was finalized leaves payroll paying full salary for days not worked while the leave still debits the balance into a negative the pay run never recovers, and a region-wide change with no CA-only marker exposes AU, UK, SG and MY retro requests to the same drop.
- **Stamp a leave balance report with the latest successfully synced pay run (max pay period end date) and run the balance-report sync only after all of that period's pay runs have synced** — a report built mid-sync shows an `as_of_date` from a partially applied period, so HR reports a balance that does not match the payroll the employee was paid against.
- **Load every query that builds a leave report inside one `DatabaseReplica.with_read_slaves` block and check that none of the remaining calls escape to the primary** — the block covers only what is lexically inside it, so a helper method that queries outside sends the whole org's leave reads to the primary at exactly the moment an admin opens the report. Require index coverage and a load test before accepting a report query that deduplicates or sorts across several columns: a deduplication `ORDER BY` spanning four fields with no covering index sorts in memory and spills to disk while an admin report loads every member in the organisation, a cost invisible in a small sandbox that lands on the shared database in production.
- **An export and its on-screen report share one scope filter.** The Time Off Taken export omitted the reporting-employee scope the screen applied correctly, because each surface carried its own filter logic (LS-33, CXP-16508, a priority-zero security report). Compare exported rows against the screen for a reporter with a restricted scope.

## Scenario coverage

- **Name the matrix cells a leave change touches, and which of them stay untested.** Actor (employee, manager, restricted manager, contractor, admin, owner, CSS user) × paradigm (HR Standalone UK/SG/MY/CA, HR+PY KeyPay/Xero/MYOB, AIO) × approval path (legacy, workflow engine, admin override, self-submit, proxy submit) × request state (create, proxy create, edit, delete, cancel, partially approved, locked) × balance surface (accrued, pending, approved, forecast, carryover, anniversary, adjustment) × payroll provider × data boundary (NULL FTE, nil date, zero balance, NaN input, disabled category) × permission scope (self, manager, CSS, reporting). An untested cell is the recurring root cause behind the incidents this file is written from, and the role × paradigm pair alone does not cover the actor dimension.
- **Treat an identity-switching change in one path as a change to every actor that can be the updater.** One fix changed the auto-approval check from the creator to the updater and broke a different actor's path three days later; the two incidents are the same lesson.
- **Treat incomplete scenario coverage, an assumed shared contract, and missing domain monitoring as findings in their own right** on a change that crosses the Leave–Workflow or the Leave–Payroll boundary, rather than as test gaps to note at the end.

# Jobs and queues

## Transactional enqueue, outbox, and idempotency

- Never enqueue or publish from an open transaction when the consumer depends on uncommitted state. Use after-commit for acceptable best-effort work or a transactional outbox when database state and event production must not diverge. Sidekiq pushes to Redis immediately, so a job enqueued inside `ActiveRecord::Base.transaction` executes before the commit: the worker reads stale or missing data, or the transaction rolls back and the job still runs. Model-level `after_commit` enqueues are correct; service-level `transaction do ... perform_async` slips through.
- Pair a business-critical outbox with consumer idempotency. For non-idempotent aggregation, persist the inbox/idempotency marker in the same transaction as the business update.
- Select reliability machinery from explicit business criticality. Outbox/inbox and durable coordination add cost; simpler at-least-once behavior is valid when duplicate or loss impact is consciously accepted.
- Make multi-step states recoverable. A crash between `processing`, an external effect, and `completed` must converge through idempotency, leases, reconciliation, or a durable state machine.
- Treat a timeout or 5xx after a mutating external call as an ambiguous outcome, not proof that the effect failed. Carry one stable idempotency key across service and processor boundaries, or provide durable reconciliation before retrying.
- In sliced batches, define partial-success semantics: retrying a whole request after earlier slices committed must not duplicate effects or hide which items succeeded.
- Never derive idempotency keys from payload contents — generate a nonce at event creation and propagate it. Payload hashes collide naturally because identical payloads occur for distinct events, and they are unstable across deploys because `#to_json` of nested values can change, so the same event redelivered after a deploy fails dedup.
- Prefer natural idempotency keys already in the unit of work (e.g. `uid` + `version`, a notification id) over a generic message_id, and wrap dedup-record insertion in the same transaction as the business update — never an explicit removal step, which leaves stale records if the process dies before cleanup. Grouping and partition keys must not be reused as single-use dedup identifiers.
- Outbox publish failure must block progress for the affected partition key — retry indefinitely, never skip or reorder. A publish or ack failure that is swallowed silently loses the event.
- Enforce outbox dequeue only inside an application transaction with a fail-fast guard, such as raising when no caller-owned transaction exists. The dequeue or claim of outbox rows must run in the same transaction as the business write.
- Separate `event_type` from `topic`: several distinct event types on a single topic preserve relative ordering within a partition, while mapping event_type 1:1 to a topic destroys the ability to keep related events ordered.
- `after_destroy_commit` publish failure loses the event forever; a producer-side guarantee requires a transactional outbox. Consumer-side reliability is useless if the event is never produced.
- Work moved into an `after_commit` or `after_destroy_commit` callback runs for every caller of that save or destroy, and it can no longer roll back with the record. Moving the sandbox-organisation and user teardown into `Member`'s `after_destroy_commit` puts it on transfers, the membership-move handler and the org-destroy cascade alike, and a raise inside the callback leaves the member deleted with the teardown half-done and no retry point. Inventory the callers of the record's destroy and name the partial-failure path — an idempotent worker, a reconciliation guard, or a stated accepted risk — before approving. Suppress when the callback body is guarded by a condition only the intended caller meets.
- Events must be self-contained. A consumer that must fetch a separately-synced workflow or entity definition creates a hidden deployment-order dependency.
- Kafka at-least-once redelivery corrupts stateful aggregation such as parallel Welford: the same chunk processed twice inflates `count`/`m2` and silently produces wrong results with no error. Apply the inbox pattern — insert `(partition_key, entity_id, chunk_index)` with `ON CONFLICT DO NOTHING RETURNING id` in the same transaction as the accumulator state update and skip when the insert returns nothing. That requires a stable chunk_index from the producer and accumulator state in the database, not Redis, so dedup and state share one transaction boundary.

## Payload contracts and worker signatures

- Pass only stable JSON-native arguments to workers. Prefer identifiers over serialized records or evolving cursor structures when jobs can wait in a queue across deployments.
- Treat a worker `perform` signature change — adding, removing, or reordering arguments — and a worker class rename as a contract change. Sidekiq stores the class name and serialized args in the queued job, so a rename or a reordered or removed arg breaks jobs already queued across a deploy. Inventory every enqueue call site and every consumer of the payload, and verify old queued jobs still deserialize.
- A new caller-supplied argument that selects a security-sensitive or privileged path (e.g. `force_refresh`) must be re-verified inside the worker against the same eligibility the endpoint enforced. Do not trust a boolean serialized into the job — console, consumer, and test code can enqueue the worker directly — and re-check the member's current state at execution time.
- When adding a new privileged branch to a worker, its guard must match the full eligibility of the existing guarded path, not a subset: a guard checking only `payroll_connected?` while the existing branch also requires `payroll_info&.keypay?` and no existing payslips lets the new path run for members the old path would reject.

## Rolling deploy and legacy unique-job locks

- Worker class rename or removal is a two-phase deploy: keep the old constant alive (alias `OldWorker = NewWorker` or an empty shim) until queues, retry set, scheduled set, and dead set are empty. Sidekiq persists the class name string in every Redis payload, so a rolling deploy enqueues the new class while old workers still run, and jobs in the retry and scheduled sets reference the old constant for days — `NameError` storms and zombie-job leaks rather than an immediate crash.
- Changing `sidekiq_options` (retry count, queue, retry_queue, dead) is forward-only: retry count and queue are serialized into each payload at enqueue time, so lowering `retry: 25` to `retry: 3` does not stop already-retrying jobs, and moving a worker to a new queue leaves old queued jobs in the old queue, unprocessed if that queue is removed from `sidekiq.yml`. Drain or purge the retry and scheduled sets as part of the change.
- Legacy code only: unique-jobs locks are best-effort; verify lock strategy and `lock_ttl` against queue latency and schedule delay, because the gem is already in use and a migration is the fix rather than a tuning change. When `lock_ttl` expires before processing, `until_and_while_executing` silently drops the job with no exception, no retry, and no dead-set entry; a crashed process leaves `until_executed` locks behind, blocking every future job with that digest until manual Redis cleanup. For `perform_at`/`perform_in` jobs the effective TTL is `lock_ttl` plus time-until-scheduled, so far-future schedules can dedupe the next run away.
- Legacy code only: the unique-jobs Reaper can delete a lock it mistakes for orphaned before the job executes, after which the job logs "started and completed successfully" but never runs. The Reaper skips cleanup when orphan locks exceed 999, when queues are full, or on timeout; with `lock_ttl` nil (the default) locks never expire, so a Redis OOM leaves thousands of non-expiring locks. Set a global `lock_ttl` and verify Reaper config against queue latency.
- Legacy code only: `lock_timeout` with a sync lock blocks a Redis connection for the full timeout: with `wait` nil the lock is synchronous (`primed_sync`), so a `lock_timeout` of seconds to minutes on a web-request path holds a Redis connection and produces multi-minute request times. Do not use it on request paths.

## Retry semantics and iteration

- Retry exhaustion is silent by default: give every worker an explicit `sidekiq_retries_exhausted` or death handler, or monitoring. `retry: false` and `dead: false` mean the job is permanently discarded with no trace, and the dead set is capped at 10,000 jobs or 6 months and then silently discards. Payroll, billing, and compliance workers with `retry: false` fail permanently with no recovery path.
- Symbol-keyed hash args are a production-only time bomb: `SomeWorker.new.perform({key: 1})` works because symbols are preserved, but `perform_async` JSON-round-trips the hash to string keys, so perform raises NoMethodError or KeyError in production. With `Sidekiq.strict_args!(false)` the bad payload is enqueued silently instead of rejected. Test workers through `perform_async` plus drain so serialization is exercised, and use string keys or `with_indifferent_access` in perform.
- Renaming a key inside an args hash, or changing nil-versus-default handling of an argument, is a payload contract change even when the `perform` signature is unchanged. Old queued and retrying jobs carry the old hash shape, so make perform tolerant of both shapes during the transition and inventory old queued jobs; the breakage is delayed and gets attributed to the wrong deploy.
- Know the retry-count semantics exactly: `retry: 5` means 6 total attempts, `retry_count` is nil on the first run and 0 on the first retry, and `retry: 0` (dead set) is not the same as `retry: false` (silently discarded). `sidekiq_retry_in` and `sidekiq_retries_exhausted` blocks that assume the count starts at 1 are off by one, and `sidekiq_retry_in` never runs on the final attempt.
- Workers iterating collections must stream: use `find_each` without `includes` (eager loading is silently ignored by batching, so it becomes N+1), cap batch sizes, and never accumulate results in an instance variable. This works in development and staging with small data and OOMs only at production scale.
- Server middleware must not rely on payload mutations surviving retries, and client middleware must not be assumed to run for retried or scheduled jobs: Sidekiq strips keys added by server middleware on retry and does not re-invoke client middleware when the poller re-enqueues. Idempotency must live inside perform.
- Avoid `backtrace: true` or any large backtrace setting on high-retry workers; cap it (`backtrace: 20`) or rely on the error service. Full backtraces are stored in every retry payload, so a large retry set grows Redis memory unboundedly.
- Manual retry loops that re-enqueue with a count arg (`self.class.perform_in(delay, count + 1)`) must make the count optional with a safe default and a hard cap, and should prefer Sidekiq's native retry machinery. The count lives in the payload rather than in Sidekiq's retry state, so a second call site that omits it yields nil, an infinite re-enqueue loop, or an immediate give-up that the Retry and Dead UI never shows.
- Pick one retry mechanism. Manual re-enqueue (`perform_in`/`perform_at` inside perform) plus Sidekiq's own retry causes job multiplication or double execution: a job that re-schedules itself on rate-limit or lock contention and also has retry enabled re-runs perform on every retry, each time scheduling another job. An ensure-block re-enqueue with `retry: false` runs the job twice, once failed and once re-enqueued, with the original failure invisible.
- Chunk `push_bulk` and `perform_bulk` calls: building a giant args array in memory then bulk-pushing doubles memory and creates oversized Redis payloads, and one invalid arg in the middle fails the batch. Validate every arg before the push.
- Sidekiq batches: never chain the next stage on `complete`, which fires after the first attempt rather than after retries resolve. Use `success` plus `death` callbacks, check `status.failures`, never create empty batches, and note that batch callbacks do not run in tests without explicitly adding the Batch::Server middleware.
- When a worker writes to a model that has `after_commit` enqueues, check for job feedback loops and add a guard: worker A updates a record, `after_commit` enqueues worker B, worker B updates the same record and re-enqueues worker A. The enqueue is invisible in the worker's diff because it lives in the model's callback list.

## Error classification and failure handling

- A worker that rescues `StandardError`, reports to the error service, and returns without re-raising silently disables Sidekiq retry: transient failures become permanent, and the "handled" error hides the systemic issue.
- Never `sleep()` inside a worker: in-worker retry loops with sleep block Sidekiq threads and hold database connections, collapsing concurrency and exhausting the pool. With concurrency near pool size a few sleeping jobs starve the pool, every other job raises `ActiveRecord::ConnectionTimeoutError`, and their retries make it worse. Defer with `perform_in`/`perform_at`, and never sleep on the success path.
- Any `Thread.current` write in a worker must be paired with an ensure reset, because state held on the thread leaks across jobs: a worker sets `Thread.current[:current_member_id]` and a later job reads stale context, giving wrong tenant or member scoping, wrong audit attribution, or cross-tenant access. Single-threaded tests never catch it.
- `Current.auth`, or any `CurrentAttributes`, must be reset between jobs on the same thread: GoodJob threads are reused across executions and do not traverse the Rack middleware chain. Add `around_perform { Current.reset; yield }` to the base job class, or a job that sets auth context leaks it to the next job — wrong-org identity, wrong audit attribution.
- Dedupe and idempotency keys must include a canonical key derived from the job's args. A class-plus-queue key collides across different payloads and drops legitimate work: `redis.set("worker:dedupe:#{class}:#{queue}", 1, nx: true, ex: 60)` silently skips the second of two different events arriving within 60 seconds. Failing open on Redis errors lets duplicates run concurrently during outages, the opposite guarantee.

## Scheduling, adapters, and worker health

- Scheduler jobs that enqueue a day's worth of jobs upfront must be idempotent across retries, and cron timezone must be explicit. A daily scheduler re-enqueues all 96 jobs at `(i * interval).seconds.from_now` on every retry unless the run is made idempotent with a database uniqueness constraint or an idempotency key; a late cron fire shifts the whole day's schedule; cron in server timezone versus business timezone fires at the wrong wall time and DST shifts every run.
- Schedule notifications as database rows with an indexed `due_at` plus a cron sweep instead of flooding Redis with jobs and cancellation tokens; rescheduling is then a row update, not a token lifecycle.
- When a worker crosses adapters (Sidekiq to ActiveJob or GoodJob), verify arg deserialization, retry layering, and queue semantics. A worker that receives an Active Record object now raises `ActiveJob::DeserializationError` on deleted records instead of handling nil, `retry_on` stacks on Sidekiq's own backoff and multiplies total retries, and `queue_as` names missing from the Sidekiq queue list leave jobs unprocessed. The diff shows only the inheritance line changed.
- Test the same entry point production uses: `perform_inline` runs client middleware while `.new.perform` does not, and `Sidekiq::Testing.fake!` never exercises retry or dead-letter paths. A `perform_inline` test can be rejected by sidekiq-unique-jobs on a lock conflict and fail for a reason unrelated to the code, while `.new.perform` skips the real path of around_perform callbacks and middleware.
- Verify worker class names resolve under the application's Zeitwerk inflector and eager-load paths. Sidekiq stores the class name as a string, so `constantize` raises `NameError` at execution time — an acronym mismatch, an ignored path, or a renamed file left behind — and the job dies in the dead set hours after enqueue with no enqueue-time error.
- Classify errors as transient, permanent, poisoned, or unknown. Retry only when another attempt can change the outcome, cap attempts from the business or SLO limit, and preserve exact exception context. Treat dependency throttling separately from code-error retry when their recovery budgets differ: a throttled job may acknowledge the attempt and reschedule for `retry_after` plus jitter, but it needs its own bounded counter, terminal alert path, and deduplication covering scheduled as well as retry sets.
- Keep expected adaptation out of delivery-error budgets: splitting an oversized batch or rescheduling a throttled job is a control path, and consuming the real failure counter can terminate otherwise deliverable work.
- A maximum of five retries is current guidance for several organisation-scoped flows, not a universal Sidekiq default; use the worker's own contract when it differs.
- Preserve partial progress for large jobs, and never retry already-completed items after one item or slice fails. Batched jobs: handle each item's exception individually so one bad record does not block the rest, collect failures and retry only the unresolved subset, and treat not-found as a soft skip.

## Capacity, middleware, and kill switches

- Set queue, concurrency, and batch size from workload, tenant size, dependency capacity, queue latency, and OOM history. Prevent duplicate and infinite work before raising concurrency, and model downstream capacity before increasing producers or replicas.
- Do not accept `:weight` or per-queue `:concurrency` changes in `config/sidekiq.yml` as a capacity change: each queue runs its own process, so those settings are often inert and the real lever is replica counts in `application-infrastructure`.
- Stage a queue or worker capacity change behind a smaller first wave, with alerts on the queues' infrastructure resource usage and latency before widening. Capacity changes shift CPU, memory, Redis, and latency for every worker on shared infrastructure.
- Scope middleware narrowly: global server and client middleware affects every job, and its setup failures can fail unrelated work. Review middleware for double yield, swallowed corruption, request-path enqueue exceptions, and fail-open or fail-closed behavior.
- Middleware order defines failure classification, and a backpressure or kill-switch middleware firing after sidekiq-unique-jobs acquires its client lock leaves orphaned unique locks that silently drop duplicates for hours. Verify ordering against unique-lock acquisition and internal reschedules, and assert the relative order of safety middleware in specs, because a swap silently inverts safety guarantees.
- An execute-side kill switch that returns without raising permanently destroys jobs under reliable fetch (`super_fetch!`): Sidekiq may move the job out of the in-progress sorted set and ack it as done, so nothing re-enqueues it when the switch clears. Any middleware that suppresses a job on the execute side must raise so the job is retried, or park and reschedule.
- Enqueue-side backpressure middleware that raises `EnqueueBlockedError` surfaces as 500s to end users on web and API requests, because the middleware sits in front of every `perform_async` call. Document the failure contract of every enqueue call site.
- Kill-switch and circuit-breaker client middleware must not silently drop poller-driven re-enqueues of retry or scheduled jobs: the poller's re-enqueue path is also intercepted by client middleware. Never silently drop correctness-critical work through a kill switch. A controlled emergency bypass is acceptable only with a named path, owner, audit trail, expiry, recovery process, and reprocessing plan, and the worker classes safe to kill must be documented.

## Bookkeeping, duplicate work, and incident response

- A worker's final bookkeeping write is itself a failure point: if it uses `update!` and raises, Sidekiq retries the whole job and duplicates external side effects. Use `update_column` plus an explicit audit for bookkeeping writes, or make them idempotent.
- Before relying on Sidekiq retry for a sync worker, verify the external system's create and update are idempotent; otherwise a retry duplicates the external effect and a lock is required.
- Verify the worker's rescue actually names the typed exceptions before claiming the service handles them: a bare re-raise means every retry notifies and the typed-error claim is false. Do not retry non-transient errors: set `retry: false` on workers whose failures are permanent (validation, argument errors) and use a per-record state machine (pending, retrying, failed with error_code) so the UI can show sync status and ordering is preserved.
- Runaway enqueue: diagnose by JID signature before acting, because a retry storm (the same JID repeated), a self-reschedule, and an external re-enqueue need different kill steps. Cut the producer before deleting, and never delete legitimate work — payroll, compliance, irreversible transitions — without a data-integrity check.
- Strict-ordering, database-backed event processing should not run on Sidekiq: its parallelism and retry semantics fight row-level ordering. Use a dedicated replicable worker with row-level locks when the database is the authoritative event source.
- `update_columns` that bypass a state machine skip after-transition hooks and audit callbacks, so an operator-triggered reset produces no audit trail and incomplete side effects. Define a legitimate transition, or add an explicit audit write and document why the transition is not used.
- Trace duplicate work to its source. A worker debounce may suppress queue effects while leaving repeated database writes, callbacks, or upstream calls untouched; repeated mailer work can both spam customers and load the database. Verify current logs even when a remediation card is marked complete.
- Prevent unnecessary enqueueing at the caller when the condition is authoritative there; do not spend queue resources only to reject immediately in the worker. Quarantine a poison or rogue worker or message rather than retrying it indefinitely or letting it monopolize shared capacity.
- Put explicit connect, pool-checkout, read, write, and overall deadlines around external calls as applicable; a single generic timeout rarely covers all blocking points. Do not add inline retries that unpredictably extend request latency or worker occupancy; bound retry attempts by the caller deadline and the dependency's rate limit.
- Disable the retry loop built into a third-party client and raise rate limits as errors, so one layer owns retry policy. Client-level retries that are swallowed turn a dependency outage into seconds of added latency on every authenticated request and stack extra attempts on the caller's own policy.
- Propagate or route exact errors at the correct boundary. Broad rescue is acceptable at a process boundary only when it reports and re-raises, retries, dead-letters, or returns a documented fallback.
- A circuit breaker is conditional on repeated dependency failures and a meaningful fallback or fast-fail benefit; do not require one for a low-volume call with no fallback merely as a pattern.
- Require evidence for dependency and queue capacity: traffic, p95/p99 latency, error rate, saturation, consumer lag, recovery time, and downstream limits. Log and alert on silent degradation such as replica fallback, bounded-cache refusal, or fail-open operation when it can hide lost capacity or double load.

## Redis, coordination, and observability

- Prefer durable database state for correctness-critical completion, delivery, and ownership. Redis is appropriate only when eviction, expiry, restart, or partial failure is acceptable or recoverable.
- Redis eviction is silent: on a store holding job or queue data, prefer `noeviction` so writes fail loudly instead of throwing away in-flight job data. Do not store aggregation or coordination state in Redis when eviction drops state without raising; use a database row with an atomic countdown.
- For Redis, review connection, checkout, read, and write timeouts separately, and verify pool capacity and failure behavior under saturation.
- For in-process caches, inspect thread and process concurrency, object mutation, tenant and key scope, invalidation, memory bounds, deployment skew, and test isolation. A short TTL does not make cached authorization or mutable state correct; preserve the authoritative source, mutation invalidation, and explicit fail-open or fail-closed behavior.
- Use one owner for a coordination invariant. Multiple stores, limiters, or completion markers need explicit precedence and reconciliation.
- Distributed locking: prefer the datastore of record — if the workflow affects PostgreSQL data, use `pg_advisory_lock` (or a dedicated locks table) inside the same transaction over a lock in an external store. Treat Redlock and Redis `SETNX` locks as low-stakes-only because of clock-skew and replication assumptions. Renew leases actively before expiry, have losers retry with backoff and log contention metrics, and for non-bigint domain IDs compute a 64-bit hash of the ID for the advisory-lock key. Prefer advisory locks over indiscriminate `FOR UPDATE` row locks to avoid deadlocks.
- Add jitter to cache-refresh scheduling so a refresh scheduled on every read or at boot does not fire in lockstep across replicas, and prime consumer caches before traffic: a cache read before the cache is populated returns misses.
- Workflow tracing: one `trace_id` per workflow inherited from the trigger event, with a `span_id` per atomic unit of work. Collect span data now even if it is not visualized, because deferring it forces traces to stand in for step-level instrumentation.
- A per-job middleware lookup must declare which database role it uses, and rollout must monitor that role — primary, not replica — with a named off switch. The lookup takes a primary connection for every opted-in job, including jobs that start in `with_read_slaves`, so a fleet-wide rollout multiplies primary queries and appears as primary CPU and memory rather than replica lag.
- Cover any middleware that reads job context from positional `args` with a spec asserting the declared parameter is present in `perform`'s positional params. A parameter rename makes the middleware log once per process and silently stay off for that worker; a reorder makes it read the wrong argument, such as the wrong org context. Neither raises.
- Make a self-disabling middleware's failure attributable: log the failing step, `worker_class`, and the non-PII arg, instead of one hypothesis-specific message that sends on-call to the wrong subsystem. A log emitted once per process makes a silently disabled feature indistinguishable from a working one.

### Job uniqueness (org rule `#EH-BACKGROUND-JOBS-BLOCKING-PREVENTION`)

- New code must not use the `sidekiq-unique-jobs` gem. The organisation's rule forbids it outright: none of `lock: :until_executed`, `lock: :until_and_while_executing`, or any other strategy from that gem.
- Reach for a non-blocking uniqueness mechanism instead: a database uniqueness constraint, an idempotency key, or a custom non-blocking Redis check. When none of those fits the contract, the owner is the squad architect rather than a lock option.
- The mechanism behind the rule: Redis `BLPOP`-style locking holds the client connection while it waits for the lock, for the whole `lock_timeout`. A `lock_timeout` of 300 seconds is a five-minute API response, and some configurations run the job synchronously on the request path. An approve endpoint was measured at five minutes from a 300-second timeout.
- The lock-specific failure modes in the bullets above — TTL expiry dropping a job silently, the Reaper deleting a live lock, `lock_timeout` blocking a request — apply to code that predates this rule. Report them there, and require the migration away from the gem rather than a tuning change.

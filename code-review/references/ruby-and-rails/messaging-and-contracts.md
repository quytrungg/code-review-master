# Messaging and contracts

- Name Kafka topics from the producer's service and entity ownership by default, and document message direction. Command topics, temporary migration topics, and opposite-direction flows can justify `Sync`, `Notification`, or `Temporary`-style exceptions; document the contract and the retirement path.
- Name a topic `<dataset>[.<module>].<entity>[.<suffix>]`. The first segment is the owning dataset — never a consumer, and never a first producer when the capability is owned elsewhere — kept when the service owns the entity and dropped when it is merely the first adopter, with the change saying which. The middle module slot carries a feature or domain partition (`ReportsData`, `WorkflowEngine`, `FaceLivenessDetection`), the entity slot carries a model or a capability, and any suffix comes from a closed list. Place the segments positionally (`<dataset>.<module>.<entity>[.<suffix>]`) and keep a feature name out of the dataset slot and a proto message name out of every slot: `HolidaySync.HolidaySetPayload` names the flow and the wire type while the reader needs the owning service and the model.
- Require the table or model that maps to a topic name before accepting it, and check that the entity exists in the service the prefix names. When no persisted entity exists, name the topic by capability and direction (`Request`/`Response`) instead of inventing one; a topic named for an entity no service owns has no owner to change the payload and no model a search can find.
- Keep a state transition out of the topic name and carry it in a payload `event` string or an `action_type`/`status` enum, while a state family may appear: `Status` and `StatusChanged` are legal, outcome names such as `Onboarded`, `Churned`, `Failure`, and `ReadyForReview` are not, and the 31 pre-MM2 names that do carry them are grandfathered and never copied. Reject an action verb in the entity position — `<Entity>Result` or `<Entity>Send` cannot carry the next event for that entity. When the current proto has no event field, extend the proto or reuse `LodgementStatusChanged`.
- Treat a topic name as a one-way door and settle the naming question before merge: a rename means deleting the topic and repointing the publisher, consumer, and proto constants.
- Apply a naming decision — entity form, module prefix, suffix — to every sibling entity in the module and on both the producing and consuming side in the same change, not just the topic under discussion. A name right on one side and wrong on the other cannot be found by searching either codebase.
- Place each topic definition in the terraform file of its producer, selected by the topic's first component, never in the file of the service that consumes it. Only `EmploymentHero`-prefixed topics belong in that producer file; the rest stay in their own domain's file. The resource is syntactically valid in either file, and the wrong home is only found by comparing the prefix against the filename.
- Prefer an existing topic plus a new event type when entity ownership and ordering match. Create a new topic when ownership, retention, access, scale, or independent ordering demands it.
- Partition count is a workload decision: model key distribution, throughput, consumer parallelism, ordering, hot keys, retention, and recovery. One partition is not a universal default, and partition count is observable contract behavior — if production has more partitions than staging, verify consumers tolerate cross-partition interleaving instead of claiming staging validated production ordering.
- Design producer pacing and consumer backpressure together: partitions, max in-flight work, dependency capacity, lag budget, throttling, pause and resume, and recovery from accumulated lag.
- Trace destroy events, callbacks, audits, and cleanup consumers before changing event production.
- Treat async state as delayed and at-least-once unless stronger evidence exists. Document staleness, ordering scope, duplicate and loss behavior, replay, and operational ownership.
- Preserve backward compatibility for every consumer, including default library behavior and consumers outside the main application.
- Treat any change to the effective consumer group id — renaming the group, changing `client_id`, or altering the consumer-mapper prefix such as `KAFKA_SUFFIX` — as an offset-reset event: the new group has no committed offsets, so it starts from `auto.offset.reset` and replays the whole topic. The diff shows only a string constant or config line; nothing errors and lag looks normal.
- Never change the event key or partition key (e.g. from `member_id` to `organisation_id`, or from UUID to database id) on a topic whose consumers rely on per-entity ordering. The key hash changes and the same entity's events scatter across partitions, so a delete can process before its create. Ordering is a runtime property, invisible in the diff; single-partition tests pass.
- Schema evolution on a shared topic must be additive-only: never remove a field, change a field's type, or add a required field without a default, because producers and consumers deploy independently. With JSON payloads and no schema registry nothing rejects an incompatible change at publish time, and renaming a field is a delete-plus-add — consumers reading the old name silently get nil.
- If a producer enables retries it must also enable idempotence, or keep `max.in.flight.requests.per.connection = 1`: retries without idempotence can reorder messages within a partition when a failed batch is resent after a later batch succeeded.
- Consumers must be idempotent against an event-identity key such as the `idempotency_key` header, not against delivery metadata: rebalance, crash-before-commit, and producer retry all redeliver the same event, and producer-side idempotence only dedupes broker writes.
- Know the provider's idempotency-key TTL: delayed retries and DLQ replays past the TTL window are treated as fresh payments. Add a TTL check in any replay path that rejects flows older than the provider window and raises a manual-review alert instead of re-submitting.
- On `RecordNotUnique` in an idempotent consumer, return the existing record so processing continues — never nil, which converts a retry into a permanently un-triggered operation with no error surfaced.
- One-shot job guards must claim atomically: insert and catch `RecordNotUnique` before `perform`, not check-then-insert, because two workers can both pass the check before the second insert fails.
- A DLQ with no consumer and no alert is a silent orphan: financial commands that exhaust retries are permanently lost. Implement a DLQ consumer that persists each dead message and fires an alert with key, topic, error, and organisation_id, plus an operator runbook for manual replay.
- Classify consumer errors as transient versus permanent before retrying or dead-lettering: never retry deserialization, validation, or schema errors, and give every retry path a bounded ceiling and a DLQ destination. A single poison message retries forever and blocks its partition while lag climbs. A DLQ without triage context — original topic, partition, offset, error, attempt count — and an explicit owner and alert is a silent backlog.
- If a retry topic or non-blocking retry is introduced, document that per-key ordering is lost: a failed message replayed later lets subsequent events for the same entity process first.
- Offset commits must happen only after side effects are durable: never commit before processing, never `mark_as_consumed` inside a rescue that swallows the error, and with `manual_offset_management` on, every path must call `mark_as_consumed`. Commit-before-process loses the message on crash, rescue-then-mark loses it on every error, and manual offset management without marking replays everything on restart.
- Set `auto.offset.reset` deliberately, preferring `latest` in production, and treat every new consumer group, expired offset, or partition addition as a point where the reset policy silently fires: with `earliest` a new group replays the entire topic, with `latest` the same events are silently skipped, and no error is raised either way.
- Topic retention must exceed the worst-case consumer downtime or lag. If a group's committed offset is trimmed by retention, the consumer gets offset-out-of-range and resets per its policy, replaying or skipping everything since the trim. Increasing partition count has the same shape: new partitions have no committed offsets, so the reset policy fires per new partition. Consumer processing time must stay under `max.poll.interval.ms` and the session timeout: long batches, blocking external calls, or per-message sleeps get the consumer kicked from the group, triggering a rebalance and reprocessing of uncommitted messages.
- Deterministic filenames for SFTP and external uploads: derive the remote path from the batch or record ID, not from a tempfile path, or a retry downloads a new tempfile with a different name and uploads a duplicate. Check for file existence before uploading and record the uploaded filename before returning success.
- Preserve Protobuf presence semantics. Trace unset versus default scalar, `optional`, wrappers, `oneof`, and `FieldMask` across producers and every consumer. Use `oneof` when regional or variant payload shapes are mutually exclusive. Do not model an invalid union as several independent optional fields, and normalize loose source types at the producer instead of weakening the shared schema.
- Reuse gRPC handlers with `FieldMask` only when authorization, validation, cost, and response semantics stay correct, and reject empty or unbounded requests early.
- Apply collection bounds before permission checks, mapping, and object construction; pagination can be omitted only when a defensible upper bound and latency and memory evidence exist.
- Gate a new service-to-service gRPC endpoint on three properties before approving exposure: the load balancer is internal-only, the hostname is bound to the mTLS gateway listener, and caller-level authorization restricts access to the intended workloads. Without all three, any workload that can resolve the name reaches the handler.
- Benchmark expensive protobuf and hash conversions on hot paths, particularly across runtime or gem-version changes.

# Data and migrations

## Schema and migration reconciliation

- Review the SQL and schema output the migration actually generates. An edited `schema.rb`, a malformed timestamp, or a migration that never ran is not proof of a working change.
- Reconcile every `schema.rb` delta to a migration in the change before judging it, then demand regeneration for anything unexplained rather than accepting hand-written content. `Database/SchemaMigrationConsistency` runs the same reconciliation in CI, so a line no migration produces is the finding and a line the change explains is not.
- Apply that reconciliation to every generated schema file in the repository, not only `db/schema.rb` — `db/authentication_schema.rb` is generated too — and ask that unrelated churn be discarded rather than reviewed, leaving only the change's own migrations.
- Verify a `schema.rb` delta against the change's own migrations before reporting a missing constraint-removal migration: a same-migration `add_column` explains a `null: true` line, and the reviewable defect may be the bundled change instead.

## Migration structure and guards

- Check a new migration's filename against the repository's timestamp-plus-verb convention and ask for regeneration when it reads as machine-invented. The filename becomes the `schema_migrations` version and is the only human index of what the migration does; an invented name also signals the timestamp is not a real generation time, which breaks ordering assumptions.
- Follow the repository's strong-migrations and DDL transaction conventions. Use `safety_assured` only for a named, understood bypass, never as boilerplate, and reject it on a plain single-column `add_column`. Never let a db-cop exemption stand in for fixing the migration. Do not request `safety_assured`, `migrate_with_lock_timeout`, or a db-cop disable on a `create_table` migration — a new table has no existing rows and no lock to bound — and never infer from a lock-timeout wrapper that a table is new. Use one `migrate_with_lock_timeout` block per migration, wrapped only around the statement that needs a raised timeout. A second block for the same logical change, or a wrapper around statements that take no lock, hides which statement holds the lock.
- Guard every schema change with the builder's existence check — `column_exists?`, `table_exists?`, `index_exists?` — so the migration is re-runnable, and treat a missing guard as a blocking finding. Inside `change_table(..., bulk: true)` use the table builder's own checks such as `t.column_exists?` and do not assume option behavior from standalone `add_column` APIs. An interrupted or re-run deploy whose schema version was not bumped otherwise raises duplicate-column.
- Change one thing per migration file, with the shape set by the table's state: a new table gets one `create_table` file with inline foreign keys; a populated table gets one file per column, foreign key, or constraint, with validations split out; a multi-column addition on a populated table gets one `change_table bulk: true` block rather than N `add_column`s. Bundling destroys diagnosability: when one `validate_foreign_key` finds orphans, PostgreSQL rolls back the sibling validation in the same file and a full scan is lost.
- For a table created in the same change, declare foreign keys inline with `t.references ... foreign_key: true` inside `create_table` and skip the add/validate migration pair; there is nothing to scan and nothing deployed, so the pair buys no safety. Keep one foreign key per file for tables that already hold rows.
- Combine compatible alterations when that reduces table rewrites or lock acquisition; isolate operations when their transaction requirements, rollback behavior, or failure recovery differ.

## Constraints, indexes, and data preconditions

- Create indexes on populated tables concurrently when the repository and database support it, put independently recoverable concurrent indexes in separate migrations, and add indexes directly during new-table creation. Index migrations must be both concurrent and idempotent: guard `add_index`/`remove_index` with `index_exists?`/`index_removed?`, set `disable_ddl_transaction!`, and pass `algorithm: :concurrently` on add and on remove. A non-idempotent index migration re-run after an interrupted deploy double-creates or fails; a non-concurrent `add_index` on a large production table blocks all writes for hours. For index replacements, deploy and verify the new index before dropping the old one. Validate production validity and query-plan use; a valid staging index does not prove production built it successfully.
- Before adding a unique or foreign-key constraint to existing data, query production-equivalent data for duplicates or orphans. A migration that works on an empty database is insufficient, and duplicate-cleanliness evidence expires: re-run the duplicate query immediately before the deploy that adds the constraint, because a week of new writes can reintroduce rows an earlier query proved absent.
- Adding a foreign key to a populated table: `add_foreign_key ... validate: false`, then `validate_foreign_key` in a separate migration after checking orphans. Inline validation scans and locks the whole table.
- Regenerate `schema.rb` after editing an already-run migration, and use the `add_foreign_key` line's option suffix as the parity test that proves the file is stale: the schema shows the validated form of a key the migration adds as `validate: false`. A table created in the same change is empty, so its foreign key can be validated at creation and `validate: false` is wrong there.
- Put the duplicate and NULL remediation for a new constraint in a comment block at the constraint in the migration file, spelled out as runnable commands — not a pointer to a thread and not "we checked" — and name every shared environment in it: production, then integration, support-01, and the sbx app environments.
- Check production first, then integration, support-01, and sbx, and reject the inference that a feature never exercised in production therefore has no data in the non-production environments. Production is the primary dataset and the only one with real volume; the shared environments are the secondary check where duplicate-remediation instructions matter.
- For shared non-production environments, include actionable duplicate detection and remediation — exact queries or a rerunnable task — whenever existing data can block a new constraint.
- Before approving a migration whose preconditions live in another change, confirm that change is deployed to production. Merged is not deployed, and an hour-old merge is not evidence.

## Column types and the column-count gate

- `CURRENT_TIMESTAMP`/`now()` defaults stamp the database session timezone, not the application timezone, so rows can be written with the wrong date. Use application-side timestamps or an explicit timezone conversion.
- Removing a column while the Active Record schema or attribute cache, or deployed code, still references it causes production errors. Follow the two-deployment process: add the column ignore in its own deploy regardless of whether the column currently looks referenced, and name the deployed ignore change in the drop migration as `@verified_column_ignored:`. Its absence is the audit signal that the first deploy never happened.
- A brand-new table with 15+ columns at creation should be decomposed immediately. The 25-column trigger applies to existing tables, but a table that starts life with 15+ columns is already a cohesion smell. Treat 25 columns as a hard gate with a written exception path, not a judgement call. `Database/ColumnCountSafety` blocks any migration that takes a table to 25 columns (`rubocop --only Database --fail-level=warning` runs on every `db/migrate` and `db/schema.rb` diff), and 61 existing tables are already over the limit and may not grow without an in-file `# rubocop:disable`.
- Count every `add_reference`/`t.references` as a new column when auditing that gate: the cop has historically counted only `add_column`/`change_table`, so an at-limit table can gain association columns and still pass CI. A clean run is not proof that the table stayed under the limit.
- Give a 25-column exception a fixed form: codeowner acceptance of the scalability risk plus a dated decomposition card linked from `schema.rb` — or decompose now. The exception must argue cohesion, access patterns, ownership, row width, write amplification, future growth, and the cost of decomposition.
- Every approved exception to a schema rule becomes a copyable precedent. Frame exceptions so they cannot be copied: named, time-bounded, and carrying a removal condition.
- Send a two-column extension of an already-wide table into a one-to-one child table named for the concept, carrying the parent foreign key plus a unique index on it. Placing the pair in the wide table keeps the new data's lifecycle indistinguishable from the parent's and pushes the table past its cap.
- Place a per-variant (per-country, per-type) foreign key on the variant table pointing at the shared row, not as one more foreign key column on the shared wide table: each new variant widens the table and the parent-side key lets a variant row exist with nothing pointing at it.
- Read a new prefix-named column (`caregiver_*`, `amounts_transferred_from_*`, `is_affecting*`) as a family decomposition signal and give the family its own concept-named table instead of one more boolean on a wide table. Decide extraction on planned near-term growth: if more members are coming, extract now; if not, defer but record it in the table's decomposition plan.

## Table and column design

- `SELECT *` queries on wide tables amplify the cost of every future column addition; the real cost of adding columns is multiplied when the codebase materializes whole rows.
- Keep primary-key types consistent across associated tables. Mixed UUID/bigint primary keys create join and type friction and long-term sync and security hazards.
- Store a calendar-only concept as `date`, not `datetime`, and do not let neighbouring `datetime` columns settle the question: a `datetime` effective date forces every consumer to interpret a timezone and infer ordering between rows to recover the intended day, and changing the type later is a data migration.
- Question a `varchar`/string column that stores a small closed set of values on a large table, and require the enum-versus-string trade-off to be stated rather than assumed: repeated strings add table and index bloat and bulk-read transfer overhead, acceptable at low row counts and a real cost on a large table. Stating the trade-off is the reviewable part; the choice is the author's.
- Adding a new enum status value requires auditing every status-based query and filter, not just the model: filters, reporting, and retention logic silently misclassify the new state.
- Bitmask columns are a data-integrity hazard: reordering, inserting, or removing a value corrupts existing rows because meaning is encoded in bit positions. Prefer join tables or explicit enum columns.
- PostgreSQL is not cache storage. Transient TTL data such as OTP digests or registration state belongs in Redis; a relational table holding short-TTL data accumulates dead tuples, WAL amplification, and autovacuum load. Check-then-act threshold enforcement is racy: two concurrent submissions can bypass caps. Lock overlapping rows or maintain a per-day counter table. Prefer join tables over `text[]` many-to-many columns: arrays lose foreign-key integrity and force scans.
- Keep reporting-only columns and derived metrics out of the operational database, and route aggregate dashboard queries to a read replica. A reporting column invites a second SLA-metric table inside the transactional schema.
- On a cross-service orchestration or migration-state table, keep only fields the orchestration logic reads — no informational counters in a JSONB details blob and no column derivable from an existing NOT NULL sibling. An informational `entries_imported_count` is general domain data the orchestrator does not decide on, and the table becomes a second, unowned copy of the source service's data.
- Stage risky renames and removals across deployments when old and new code can overlap. Include dual-write/backfill/read-switch/cleanup steps only when the actual contract requires them.
- Verify rollback where rollback is supported and expected. The `down` is mandatory wherever the reverse operation is expressible and lossless — write it for anything the database can undo, including an `add_column`; `raise IrreversibleMigration` on an `add_column` blocks `db:rollback` in development and staging with no technical reason, and is correct only where the reverse loses data or cannot be expressed safely; a policy-wide exception is stated in the change description rather than assumed as a default. `MIGRATIONS_WITH_LOCK_TIMEOUT` in `config/initializers/strong_migrations.rb` forces an explicit `up`/`down` pair precisely so the reverse is written by construction.

## Locks, backfills, and deploying DDL

- Analyze lock, scan, table rewrite, backfill, and replication impact. For large verification queries, prefer a safe replica when semantics allow, apply a statement timeout, inspect `EXPLAIN` before broad scans, and require zero violating rows.
- Deploy lock-taking DDL on a large or busy table inside the low-traffic window, with monitoring and a stated revert. The window decides when the deploy runs, not whether the work may be deferred: the migration code is identical at 88k rows and at millions, so contention, lock pressure, throttling, and whether the job needs ops supervision are what the window changes. Run the backfill or risky DDL now while the table is small and quiet, and challenge any plan that defers the work itself to a later sprint. "Low traffic" is the argument for doing it now, not for postponing it, and every deferred decomposition hands a zero-headroom schema to whoever adds the next column.
- Demand the production row count before accepting a backfill's execution plan: the count, not the author's confidence, decides between inline migration, rake task, and manual run. "A small table with a few records" without a number is not sizing evidence. Run a backfill in production first by hand, then land the guarded version that early-returns in production so non-production pipelines are not blocked. A backfill that runs inside the deploy pipeline on every environment blocks the production deploy behind a scan nobody asked for.
- Use database constraints as the primary protection for concurrent data invariants: choose uniqueness, exclusion, foreign-key, or check constraints before adding distributed locks. Use application locks only for behavioral sequencing that cannot be expressed as a database invariant, and choose optimistic, pessimistic, or idempotent coordination from the contention and failure model.
- Add foreign keys for real ownership relationships unless there is an explicit cross-database, lifecycle, or operational reason not to. During table creation, prefer the repository's reference helpers.
- Backfill existing rows before enforcing `NOT NULL` where the database cannot safely do both. Distinguish a column default from the fourth argument of Rails `change_column_null`. Split `NOT NULL` validation from final enforcement when a large or busy table needs independently retryable scans and lock acquisition. Do not impose the maximal multi-migration pattern on small or quiet tables without evidence.
- Decompose a table when fields have a distinct lifecycle, ownership boundary, access pattern, or reusable domain concept. A properly indexed join is not itself evidence against decomposition.
- Do not add speculative columns for unapproved future work; the schema should represent current contracts.
- For dual writes, compare model callbacks and setters with database triggers. Account for direct SQL and validation-bypassing writes, transactional atomicity, observability, schema visibility, and removal conditions.
- Prove old-column/new-column equality in production before removing the dual write and adding `ignored_columns`: the teardown deletes the only mechanism keeping the columns in sync, and if the backfill missed rows the old column is the last copy and the loss becomes invisible once `ignored_columns` lands.

## Schema shape and post-create data

- Use Rails polymorphic references only when the domain genuinely spans entity types and the integrity/ownership trade-off is accepted. Consider AASM only when the repository already uses it and explicit transitions, guards, or auditability justify a state machine. A status column alone is not proof that AASM is required.
- Treat a copied organisation or tenant id on a child table as a data-integrity defect and fetch the org through the not-null association instead: a duplicated parent id goes stale the moment the parent's value is corrected, and nothing detects the divergence.
- Before accepting a new column, test whether the value is already reachable through an existing association or already expressible by an existing seeded lookup column. On `candidate_jobs` the proposed career-page column returned exactly the row `candidate_job.job&.hero_foundation_career_page_job` already returns, and the applicant-channel need was already covered by the seeded `DefaultCandidateSource` values behind `candidate_source_id`.
- Require a named retention window enforced by a scheduled purge for every new append-only stats, event, or receipt table. Deferred partitioning is acceptable only if the retention policy is decided now; purging after six months was the concrete ask for a table holding one row per org per day with no bound.
- When a newly added column will be filtered on by live traffic, deploy the index before the code that queries it. Merging both means the first production requests after deploy run unindexed on a populated table.
- Bind every post-create data-initialization step to the resource's replacement path, not only to the workflow that first created it: a database host replaced by a crash, OOM, or service replace comes up healthy and empty, so health checks pass while every resource pointed at it has no data.

## Query paths, reads, and pagination

- Check serializers, loops, callbacks, and views for N+1 queries, and select `includes`, `preload`, or `eager_load` from the actual query contract.
- Verify the actual association call chain: applying a new scope to an already-preloaded association can issue a fresh query and reintroduce N+1 behavior.
- Select only needed data on hot paths, but do not replace object loading with `pluck` when callbacks, types, or model behavior are required.
- Require workload and SLO evidence for slow-query findings. A historical duration threshold is a signal to inspect plans, cardinality, buffers, indexes, and caching, not a universal correctness rule.
- Route reads by semantics, not current replication lag: read-after-write, financial calculation, session or token validation, a permission check gating a write, and idempotency checks belong on the primary. Keep related reads sticky to one replica or role for an execution unit. Per-query balancing across replicas can assemble an internally inconsistent result from different WAL positions. Pick one replica per feature and stick to it rather than load balancing automatically, and check replica health — CPU, freeable RAM, lag — before pinning.
- Never place writes or service calls inside a read-only replica block, and verify fallback behavior when replicas are unhealthy.
- Enforce a primary-read contract in the class that owns it, not through caller discipline. `DatabaseReplica.with_read_slaves` wraps a block in `ActiveRecord::Base.connected_to(role: :reading_from_replica, prevent_writes: true)` (`lib/database_replica.rb`), and `ApplicationRecord` maps roles through `connects_to database: { writing: :primary, reading: :primary }` plus one entry per configured replica, so every `model.connection` or `select_all` read inherits whatever role the caller set. A service whose purpose or comment says it reads the primary — a value compared immediately after a sync, a financial figure — must pin it with `ActiveRecord::Base.connected_to(role: :writing) { ... }`. Nesting a different role appends a frame to the stack rather than raising, so the pin holds inside a read-slave block and is a no-op only outside one. When a change removes such a pin as a no-op, ask which caller was active, and treat a class comment promising primary reads without the pin as an unenforced contract.

## Pagination, limits, and index alignment

- Treat offset pagination beyond 1,000 as a review gate: require a bounded administrative use case or stable keyset/cursor pagination, and do not infer safety from total table size alone. Every customer-facing list API must enforce a hard, server-side, non-client-overridable upper bound on results, even paginated APIs. Optional bounds with no defaults silently mean "fetch everything": a null date range or null pagination materializes the whole table and OOMs. Enforce bounds at the entry point — cap the date range, require a minimum filter count — because permissive filter combinations defeat any query optimization.
- A hidden global `LIMIT` is not a no-op: it alters Postgres query-planner decisions even when never hit, can introduce performance regressions, and can conflict with other query constraints. Apply any default limit explicitly and visibly at the controller or scope level.
- Human-formatted strings such as full addresses are not stable lookup keys — free-text input and vendor-formatted addresses will not match. Index and join on vendor place IDs instead.
- Reject a redundant single-column index only when an existing B-tree composite has the relevant left prefix and the target query or order can use it; column order and query shape still govern coverage.
- Align index contents with the real predicate. When a hot path reads only one lifecycle state, consider a partial index and confirm the planner uses it; indexing every status adds write and storage cost for no query benefit.
- Validate filtering and ordering semantics at boundaries: inclusive versus exclusive time ranges, `NULL` handling, stable tie-breakers, retention cutoffs, and timezone conversion.

## Writes, deletion, and data tasks

- Treat `update_column`, bulk SQL, and direct writes as validation and callback bypasses. Trace audit, Kafka, cache, search, and other downstream side effects before approving them.
- Before destroy or cascade changes, trace audits, callbacks, emitted events, uploads and object storage, and externally retained identifiers. Soft deletion is a lifecycle decision, not a default. Require retention, restoration, legal, query, uniqueness, and purge semantics.
- For bulk deletion or backfill, bound batch size, transaction duration, memory, callbacks, retries, and restart position. For imports, prefer stream parsing, validation, and batched insertion. Persist run metadata and row errors, and store every raw row in the primary database only when a concrete query, audit, or recovery contract requires it.
- CSV exports: synchronous streaming only for datasets guaranteed small (fewer than 1,000 rows) and fast (under 1 minute); anything larger or slower must be asynchronous. Even for small exports, batch database reads (`find_in_batches`) and stream rows via an `Enumerator` — never materialize the complete relation and output buffer. Set `Content-Type: text/csv`, `Content-Disposition: attachment`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`, and omit `Content-Length` for chunked streaming.
- Monetary values need exact numeric types — integers in a defined minor unit or arbitrary-precision decimals — never IEEE-754 floats, which are approximate. Integer cents is a good baseline, but domains needing fractions of the minor unit (interest, FX, proration) require fixed-precision decimal. For transport and interoperability, strings or composite representations may be appropriate.
- Keep microservice-owned data behind an explicit contract; do not reach across service databases to avoid designing an API or event flow.
- Test data-migration tasks against reruns, partial completion, representative volumes, and the exact production data shapes that can violate assumptions.

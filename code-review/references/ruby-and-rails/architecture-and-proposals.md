# Architecture and proposals

- State the problem, users, business impact, non-goals, current behavior, and measurable success criteria before selecting technology. Trace the current artifact and its transitive dependencies; later revisions, child proposals, implementation decisions, and current code can supersede the initially linked page.
- Ask clarifying questions where scope, ownership, data authority, failure tolerance, or constraints would change the decision, and do not fill material gaps with assumptions.
- Separate independent problems. Give each concern its own contract, owner, verification, and delivery path when combining them would hide risk or block rollback.
- Require decision evidence tied to SLOs, observed traffic, data shape, failure recovery, security, cost, and operational ownership.
- Preserve consistent terminology across PRD, proposal, API, schema, events, and implementation, and resolve naming collisions with existing domain concepts.
- Compare the smallest viable options against explicit criteria. Explore a missing alternative when it materially changes trade-offs; do not manufacture a third option when two exhaust the decision space.
- Include the current implementation as a baseline, and quantify what happens if the organisation does nothing.
- Separate contract parity from enhancements: first show how the named source behavior is preserved, then evaluate optional improvements independently.
- Evaluate synchronous versus asynchronous designs through availability coupling, latency, staleness, ordering, duplicate and loss semantics, replay, ownership, and support burden.
- Choose outbox, inbox, or exactly-once-like coordination only after declaring business criticality; simpler at-least-once processing is often the correct trade-off when duplicates or loss are tolerable.
- Evaluate reuse, a public dependency, an internal shared component, and in-repo code from maintenance, security, and compatibility evidence rather than a fixed preference.
- Deadline pressure can justify a controlled interim design, not an unsafe implicit contract: record the risk, owner, expiry, migration path, and rollback. When an interim fix compensates for a defect owned by another repository, also record the failing location — a line in `keypay-integration`, for instance — and the compensation to revisit once the real fix lands, or the workaround outlives its cause.
- Use resource-oriented API naming by default. An action endpoint is valid when the domain operation is not CRUD; explain the semantics and idempotency. Choose HTTP methods from safety, idempotency, replacement and patch semantics, caching, and the existing API contract rather than naming alone.
- For renamed or removed endpoints, fields, auth flows, events, or shared defaults, inventory every consumer and provide sequencing, compatibility, telemetry, rollback, and removal criteria.
- Preserve data ownership at service boundaries. Avoid direct cross-service database access; define APIs, events, replication, or read models with an authoritative owner.
- Do not infer data ownership or residency from transport choice. REST and gRPC both need an explicit authoritative owner, deployment boundary, access policy, and storage or residency contract; gRPC mainly changes interface and serialization conventions.
- For integrations with several capabilities, state whether sign-in, mail, calendar, and similar grants intentionally share one authorization account or require separate consent. Repeated authorization is a deliberate product and security contract, not an accidental model consequence.
- For table or entity renames, include dual-write, backfill, read switch, verification, and cleanup only when production overlap requires it; minor naming consistency rarely pays for that risk.
- When moving integration records, reconcile identifier models, encrypted-token re-encryption, key ownership, and collision behavior. A row copy is not a migration when UUID, primary-key, or cryptographic boundaries differ.
- For temporary dual writes, state the exact start and end conditions and ensure the interim mechanism cannot silently become permanent.
- For JWT-carried permissions, evaluate freshness, revocation, token size, trust boundaries, signing, replay, and permission churn; do not use the pattern merely to avoid an authorization call.
- Include failure modes for unavailable dependencies, lagged consumers, poison events, partial writes, stale caches, deployment skew, and operator error.
- Cross-area design: default to asynchronous communication where possible, use strategic caching and request throttling for read-heavy loads (cache close to use, generous TTL, just-in-time invalidation, throttling and deduplication to avoid load amplification), prefer lean purpose-built APIs over chaining poorly matched existing ones, implement circuit breakers and graceful retries, apply API rate limiting, ensure observability and alerting for traffic, latency, and error rates, avoid long chains of blocking interactions, use idempotent operations for distributed side effects, and use the outbox pattern for distributed data consistency.
- Event payload schema versioning: consumers must reconcile every linked version, not just the latest, before bumping, because a store can hold entities at mixed schema versions.
- Optimistic locking over events: accept the write when the echoed version matches rather than requiring consumers to increment; requiring publishers to compute version plus one invites off-by-one and race errors.
- IdP vendor selection: distinguish single sign-on from same sign-on, since SSO requires a shared domain for a shared session cookie; require just-in-time migration with user-controlled conflict resolution over big-bang migration; support multiple email addresses per user account for federated identities.
- Data residency and pseudonymization: GDPR pseudonymisation means personal data cannot be attributed to a data subject without additional information kept separately. Tokenize foundational PII fields into regional datastores and replace them in the main database with pseudonymized tokens, keeping token IDs self-describing by region, entity, and uuid.
- Service-to-service auth: prefer decentralized JWT issuance with granularly scoped keys generated just in time per call over a central issuer, whose network overhead dwarfs key generation at scale and whose outage blocks processing. Standardize key management through a shared library rather than centralizing issuance.
- Ledger and event design: model postings, of which a transfer is one use case; keep tenancy as a hard boundary enforced within the schema so sharding and partitioning stay possible, with account hierarchies as a soft roll-up convention; store running totals on immutable postings rather than materialized views; treat payload checksums and idempotency keys as independent concerns, because a checksum cannot replace a forcibly-unique reference; consider a durable queue with atomic commits such as GoodJob when prioritizing resiliency over throughput.
- Rollout strategy: a `preStop` hook is preferable to relying on SIGTERM handling alone, because the handler may run after the pod picks up more work; coupling `maxSurge` and `maxUnavailability` can degrade latency-sensitive services during deploy; expose `successThreshold` and `failureThreshold` without remapping to remove ambiguity.
- Flag implementation scope not represented in the approved requirements, but distinguish necessary support work from product expansion and seek explicit ownership instead of mechanically deleting it.
- Split delivery when changes have independent failure domains, deployments, owners, or rollback paths; size alone is not the reason.
- Identify existing code, components, endpoints, topics, and platform capabilities before adding new ones, and reuse only when semantics and ownership match.
- Define rollout, observability, alert ownership, reprocessing, rollback, cleanup, and post-deployment verification before approval, and for destructive or irreversible changes name the recovery strategy and the evidence required before crossing each deployment gate. Keep proposal claims current: identify data source, environment, revision, and observation window so a reader can judge freshness.
- An approval names the scope it covers — a file, `migration syntax only`, or the specific behavior reviewed — because approval limited to syntax or to owned files is not evidence that feature behavior, data design, or surrounding application logic was reviewed.
- A fix that exists only on another branch, another change, or a pending preview integration is unverified until it reaches the revision under review and that revision's deployment is verified.
- When a scanner or automated check flags an identifier crossing a boundary, establish where it came from and the authority gating the operation before treating the identifier as a credential. A value derived server-side from an owned record and separately gated by IAM is an ownership tag; a value accepted from HTTP parameters is a bearer credential, and reviewing the two identically produces either normalised bypasses or a real credential treated as harmless.
- Establish the repository-required source and base branch before reviewing, and send a fix to the branch that reaches the environment it repairs: production fixes go to main, never a stable or release branch, and a repository requiring `preview/*` entry means recreating the change from that branch rather than retargeting it.
- When an automated planner or generator replaces hand-maintained configuration, keep every explicit entry as a hard constraint and place only the unassigned remainder, iterating that remainder in stable identifier order so equivalent input yields identical output. Deleting explicit assignments re-homes work someone pinned deliberately, and first-fit over submission order makes the result depend on input order.
- Compute placement, port, and name resolution in a side-effect-free planning step that runs before any provisioning side effect, and pass the resulting plan into the code that renders or applies resources. A placement decision taken during task rendering can only surface a bad pairing with resources already standing.
- Write at resource creation every tag that a policy, sweep, or cleanup grant conditions on — an environment `Project` tag or a per-instance identity tag — and treat a missing tag emission as part of the same change: a condition key that creation never writes fails closed against the very resources the grant was written for.
- A raised latency, timeout, or resource ceiling on an SLO-bound shared production path is an owning-team decision, and the preferred remedy is optimizing the code path rather than lifting a limit the path is already measured against. Absorbing variance on a dedicated or preview resource is an operational decision instead: document the monitoring and the revert.
- Treat a list endpoint's page-size ceiling as a measured latency contract: get the p99 at the proposed ceiling from APM before approving a raise such as `item_per_page` to 500, and fix an over-asking consumer by lowering its page size in the consumer's repository rather than by widening the server maximum. A ceiling becomes a default because clients converge on the maximum rather than on their need.
- Require a tracking ticket for every suppression of an API-contract cop, with the ticket reference written into the inline comment. A bare disable of `EhCop/GrapePaginationMissingLimits` is an unbounded list endpoint with no owner, and the disable removes the only signal that would say so.
- Treat a new cop added to the shared `rubocop-ehcops` gem as an organisation-wide contract change: scope it with `Include:` and complete the release plumbing (CHANGELOG, `app.json` version bump, README) in the same change. Cops without `Include:` run on every `.rb` file in every consuming service on bundle update, and merging publishes whatever version `app.json` already holds.
- Derive infrastructure resource names from the environment's own name variable rather than a hardcoded default, and make the environment an optional suffix on any shared base name. A default naming the stable resource silently points every preview and CI environment at shared production infrastructure.

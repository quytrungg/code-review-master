# Reports domain review

Review rules for reporting features across the three codebases that serve them: the reports modules of the `employment-hero` main app, the `reports-service` repository, and the reports module of `frontend-core`. The sections cover field and row access, the report lifecycle, widget data and filters, exports and jobs, custom reports (build-your-own reports, BYOR) end to end, the sync from source services into reports-service, the reports-service catalog, its ingest write path, feature flags, the frontend module, and tests. Each bullet is one rule; where a rule conflicts with the code under review, the code wins.

## Orientation

Read this map before the rules, because most report defects are a value or a check that is correct in one of these layers and missing in the next.

- **Main app owns definitions and permissions.** `DashboardReport` is built from `ReportWidget` and `ReportWidgetFilter` rows. `Reports::GenerateDashboardReports.generate` syncs those rows from the declarative registry in `app/lib/reports/reports_registration/*.rb`. Build-your-own reports (BYOR, also called custom reports) are `CustomReport` behind a `DashboardReport`, with `CustomReportShare` rows for sharing, `CustomReports::Query::*` field modules, and `CustomReportFileWorker` for exports; the `Custom reports (BYOR)` section carries their rules for every layer. A `StandardReport` is a global template published to organisations through its `mode` and `standard_report_organisations`. Report access is decided in `DashboardReports::GetReportAccessibilities`, member scope comes from `PeopleReport::GetReportingMembersService` and the `MembersFinder::*Reportable` finders, widget data comes from `ReportWidgets::Fetcher` and `report_widgets/data_builders/<report>/*`, and CSV exports run through `Csv::V2` and `ReportWidgetFileWorker`.
- **Reports-service holds a reporting copy.** Source services publish to `<Source>.ReportsData.<Entity>` topics after commit, with best-effort delivery: consumers catch, report and move on, and there is no retry or dead-letter queue. Missed rows are repaired by the pull-based backfill (`Reports.BackfillRequest` / `Reports.BackfillResponse`), which replays rows as updates but never replays deletes. Rows land in sync tables, then in `dim_*`, `fact_*` and `snapshot_*` tables declared by the YAML catalog in `config/catalog/`. Query modules (`Query::<Module>`, `has_field`) define the report fields. The V1 engine (`Query::PreviewBuilder`, `Query::ExportBuilder`) and the V2 engine (`Query::ReportBuilder::BaseBuilder`, `Query::ModuleRegistry`, grain strategies) share no state. Permission keys and visible members come from the main app over gRPC.
- **Two permission paths, not one.** The ad-hoc `ExecuteQuery` RPC applies the catalog allow-list, `FieldAccessPolicy` and `FieldPermissionChecker`. A saved custom report's search, view and CSV go `report_widgets/:id/search|csv` → `ReportWidgets::GetData` → `CustomReports::Search` → `PermittedFieldsResolver`, and none of the `ExecuteQuery` checks run on that chain. `Query::ModulePermissionKeys::BY_MODULE` narrows rows on it; it does not gate fields.
- **Frontend.** `apps/hr-web-app/src/modules/reports` holds the report list (`reportList/`), the details page and widget shell (`Details/WidgetBlock.tsx`, `WidgetFilters/index.v2.tsx`), the predefined tables (`genericWidgets/ReportTable/DefaultReportTable.tsx`, `predefinedTable/<domain>/*`), and the BYOR canvas (`ReportCanvas/`). `apiCalls/` mixes Redux `useApi` calls to `dashboard_reports/*` with react-query calls to the reports-service `/preview` and `/search` endpoints. `modules/customReport` is only the legacy `/custom_reports` redirect.

## Field and row access

- **Run every column a query references through the same field permission check as the selected columns: `order_by`, `where`, `having`, group-by, aggregation fields, distinct-values lookups, and joins** — a locked field that still filters, sorts or groups shapes the result, so "salary above X" with salary cells locked still names who earns above X, and sorting by a hidden field leaks its order (PEAC-4280, confirmed on staging). Match a sensitive field by module plus alias, never by bare field name, or `Certification#status` is blocked while a sensitive field with a common name slips through. The rule does not apply to a field visible for every row in scope.
- **Take a field's employee scope from the permission group that grants that field, not from the union of every group that grants its module** — a union-scoped lock (`ReportingFieldLocks#locked_aliases_for` fed from module rows) shows new salaries for every employee to a viewer whose salary grant covers one division. Single-group viewers and Owner/Admin are unaffected.
- **Register every new report module in both permission maps, `CustomReports::ValidateFields::MODULES_TO_PERMISSION_KEYS` in the main app and `Query::ModulePermissionKeys::BY_MODULE` in reports-service** — `CustomReport#can_access_field?` returns true for a module with no entry (`return true unless permission_keys`), so the module is open on shared-report previews and exports, and a module missing from `BY_MODULE` skips the team, location and worksite narrowing the legacy report applied, so a scoped manager sees members outside their scope. The build-time default disagrees with the view-time one: `ValidateFields#module_accessable?` passes nil keys to `permissions_granted?`, which returns `active_admin_or_owner?`, so an unmapped module (KiwiSaver, TaxCodeDeclaration, LeaveLiability) can be built only by Owner/Admin and is then open to every viewer of a shared report; fix the map rather than one default. The rule does not apply to a module the main app does not row-scope.
- **Gate a catalog table with the permission key that protects the main app's own copy of the same data** — `security_permissions_personal_details` on a tax or pay table opens pay data to personal-details holders, and an admin-settings or edit-action key used as a view key (`review_settings`, `bradford_factor_management`, `asset_register_view`) either passes nobody or passes too widely. The key must exist in the main app's `MODULES_TO_PERMISSION_KEYS`: a key that appears nowhere there (`security_permissions_uk_tax_and_national_insurance`, PEAC-4295) locks every viewer out. The rule does not apply where a product decision names the key explicitly, as Expense → `expenses_management` does.
- **Port the main app's per-module `with_permission` gates and per-field gates when a module moves to reports-service** — a ported module that drops them exposes fields the main-app engine hides: Benefit (`with_permission { false }`), super amounts, `fte`, `anniversary_date`, `has_rehire_offboard`, the ATSI organisation setting, `primary_location`, and VEVO visa fields. For `rs_source` modules, country gates still live in the main app's `with_permission`, because reports-service does not apply them. The rule does not apply to fields the main app shows ungated.
- **Re-check field and row permissions on every surface that reads report rows: dashboard widgets, `WidgetDataAdapter`, pinned and severed widgets, exports, and the HeroAI reporting agent** — a new surface that reads reports-service rows without the report table's checks hands salary or bank fields to a wider audience. The acceptance test is that the surface returns no more than the report table for the same viewer.
- **Fail closed when a permission check meets a protobuf field it cannot read** — a `respond_to?` or `response_field?` guard on an `eh_protobuf` message that skips the check when the field is missing opens access to every caller on an older `eh_protobuf` version. The rule does not apply to guards on fields that carry no authorisation meaning.
- **Return no rows when the permitted-member set is empty, before it reaches a downstream service** — `GetTakenList`, `LeaveBalanceServices::GetHistoricalLeaveBalanceReportService`, `GetLeaveBalanceTransactions` and the benefits gRPC client treat `member_ids: []` and nil as "all members", so `effective_options[:member_ids] = ids.intersection(allowed)` producing `[]` shows a scoped manager the whole organisation. Return `Member.none` or exit early, and do not accept a spec asserting `hash_including(member_ids: [])` as proof, because it passes for exactly the wrong reason. The rule does not apply once the downstream code treats `[]` as "match nothing".
- **Keep `unless ids.nil?` as the guard for applying a CSS scope join or where clause, and never change it to `.blank?` or `.present?`** — `nil` means the scope does not apply and `[]` means the scope grants nothing, so `where(hr_positions: {work_site_id: ids}) unless ids.blank?` returns every member to a worksite manager with no worksites. The rule does not apply when the helper can never return `[]`.
- **Start every widget data builder from the CSS-scoped member set, never from the organisation** — use `PeopleReport::GetReportingMembersService.new(current_member, report_key: DashboardReport::<KEY>).call.reporting_members` or a `MembersFinder::*Reportable`; a builder starting from `SalaryVersion.joins(:member)` on the organisation shows members the viewer's security role hides. Aggregate side values such as `latest_year` reuse the same scope. The rule does not apply to an admin-only report whose PO has confirmed no CSS restriction.
- **Keep every guard of the fallback path on a permission fast path** — check `exclusions_released?(KEY)` before `scope_released?`, pass `include_terminated: true` where the fallback (`organisation.members.not_system`) includes terminated members, hold `admin_or_owner?` or `force_all:` on every early return in `MembersFinder::HrComplianceReportable#default_scope`, and keep `worker_type_access?` in the sidebar's `report_accessible?`. Each dropped guard is a different failure: excluded members leak, terminated rows vanish, a worksafe officer gets `Member.none`, or contractors see OKR and JobKeeper menu items.
- **OR the legacy CSS key into the check when a report moves to a dedicated or split key, until the permission backfill is confirmed** — `manage_all_leave_taken_report? || manage_all_leave_requests_report?` keeps users who hold only the old key from falling back to reporting-chain rows or losing access. The rule does not apply once the backfill has run and the flag is removed.
- **Decide report access in `DashboardReports::GetReportAccessibilities`, and update the sidebar policy in the same change while `valid_child_items?` still reads `CentralizedReportPolicy`** — `CentralizedReportPolicy` is deprecated, so a check added only there does not control access, and a check added only to the accessibilities service leaves the menu showing a report the viewer is denied.
- **Make a report policy check the owning module's flag or entitlement and the member's state, not a role alone** — start from `member_state_access?(allow_postboarding: true)`, include the module flag (`RequestFormPolicy::FEATURE_FLAG` in `RequestTicketsReportPolicy#access?`), re-check the visibility flag behind a CSS grant (`admin_or_owner? || (granted_to_use_payroll_dashboard_reports? && feature_flag_on?(:css_payroll_report))`, PEAC-3389), and give `AutopayServices::ReportPolicy` actions `accessible? && report_permitted?(...)`. Without these, offboarded members keep access, organisations without the module see the report, and a permission ticked before the flag was switched off still grants access.
- **Gate a permission-restricted main-app field with one predicate in the serializer, the table columns, the CSV transformer and the sort** — `TimesheetReportV2Serializer` listing `:full_legal_name, :base_cost, :national_insurance_cost, :pension_cost` unconditionally leaked personal and cost data, and a sortable BYOR field needs `permitted_fields.include?(linked_field)` in `PreviewBuilder`, or sorting leaks the hidden field's order. Write each gated attribute as a method that starts `return unless policy?`.
- **Select worker types with an allowlist and gate volunteers in every branch** — `where.not(worker_type: LEGACY_CONTRACTOR)` silently includes volunteers and any future worker type; write `where(worker_type: [nil] + (Member.worker_types.keys - [VOLUNTEER]))`. Every `elsif @personnel_type == Member::VOLUNTEER` branch needs `@volunteers_accessible`, an organisation-only context uses `VolunteersPolicy#use?` rather than `#access?`, and the policy scope and the query service agree on `nil`; otherwise headcounts are wrong and volunteer data is readable through `personnel_type=volunteer`.
- **Exclude soft-deleted members explicitly in the report builder's member scope with `where(deleted_at: nil)`** — `Dim::Member.not_system.where(organisation_id:)` returns soft-deleted members, `.active` reads like a deletion filter but tests member status, and `exclude_terminated_employees` does not look at `deleted_at`.

## Tenant scoping

- **Never load a report entity by id or uuid alone** — `CustomReport.find_by(id: metadata['custom_report_id'])`, `ReportWidget.find_by(uuid:)`, `ReportWidgetFilter.where(report_widget_id:)` and `CustomReport.find_by(id: source_cr_id)` in the duplicator let one organisation read or clone another's report or filters. Scope through `current_member.custom_reports` plus `GetSharedReports`, `ReportWidget.joins(:dashboard_report).where(dashboard_report: {organisation_id:})`, or `CustomReport.joins(:member).where(members: {organisation_id:})`; a `Security/DefenseIdor` disable on the line is the signal to look. The rule does not apply when the id came from an organisation-scoped relation in the same method, such as `dashboard_report.report_widgets`.
- **Assert organisation ownership in a worker that reports-service triggers over gRPC** — `ReportWidgets::TriggerComparisonSearchWorker` loading `ReportWidget.find_by(uuid: args[:widget_uuid])` and `Member.find_by(uuid: args[:member_id])` unchecked runs a widget for another organisation. Assert `member.organisation.uuid == args[:organisation_id]` and join the widget to `dashboard_reports.organisation_id`.
- **Scope secondary lookups inside field derivation and metadata by organisation** — `field.source.where(id: record_ids)` in `GetCustomReport` and `Member.find_by(id: member_id)` in `CustomReports::Query::InductionCompliance` read across organisations and crash on a nil `member.start_date`. Use `organisation.members.find_by`, and allow the ready-linked PEO organisation ids, or Global Teams host reports break.
- **Check the stored row's tenant before an upsert keyed only on `source_id` writes `organisation_id`** — `upsert(..., unique_by: :source_id)` writing `organisation_id: match.organisation.source_id` moves a row between tenants on a `source_id` collision. Include `organisation_id` in every business-scoped lookup as well: `Dim::PayrollInfo.active.where(external_id: @business_id)` alone can return another region's business, because KeyPay business ids are not unique across regions.
- **Give every reports-service table `organisation_id NOT NULL`, and reach shared template rows (null organisation) only through an organisation-owned join** — a shared row queried on its own is cross-tenant data. The exception is a shared template row reached only through such a join, named in the change and approved by the reports-service owners.
- **Filter a view or subquery joined in the V2 engine by organisation inside the join, and put `.where(organisation_id:)` before `.current_state`** — the outer `dim_members` organisation filter does not push down through a view's internal `DISTINCT ON`, so `ReportViews::PerformanceReview` scanned every tenant and timed out in production (EX-3302). Write `ReportViews::PerformanceReview.arel_table[:organisation_id].eq(ctx[:organisation_id])` in the join and `Fact::Expense.where(organisation_id: ctx[:organisation_id]).current_state`.

## Report lifecycle and models

- **Lock rows in one order across every service that mutates a published report: the report's own `DashboardReport` first, then its `StandardReport`, then the rows for the replaced legacy key** — `StandardReports::Publish` locking the legacy `DashboardReport` and the `StandardReport` rows before its own `DashboardReport`, while `ChangeOrganisations` and `UpdateDraft` lock `DashboardReport` first, deadlocks a concurrent re-publish and organisation change, and the database aborts one request with a 500. Read any "before" value for an audit event (`old_mode`, `old_ids`) after the lock, or a concurrent change records a transition that never happened.
- **Guard each lifecycle transition on the report's current state** — an unpublish on a report that is not enabled, or a second unpublish, must return 409 or do nothing without an audit event, or the audit trail records an unpublish and a `legacy_report_restored: true` that never happened. A publish on an already enabled report must either be rejected or be an explicit, tested decision, because it can rename the report, change or clear `replaces_report_key` and rewrite its organisations while bypassing the immutability `UpdateDraft` enforces.
- **Clear stale `standard_report_organisations` rows inside the same transaction that changes `StandardReport.mode`, never in `after_commit`** — an `after_commit` failure cannot roll back, so the report is left at `mode=all` beside organisation rows that readers still honour. Keep the order `create_standard_report_info! → add_standard_report! → add_widgets!`. The rule does not apply to an update that leaves `mode` unchanged.
- **Propagate the inner service's errors from `StandardReports::UpdateDraft`, and derive the admin from `is_sap_admin?` rather than an `admin_user` param** — `return unless update_service.error?` with nothing added makes the endpoint report success for a failed update, and a caller-supplied admin flag is an authorisation decision the caller makes for itself.

## Widget data, filters and queries

- **Declare every filter key and `skip_pagination` in the data builder's Dry `filters_schema`, including the shared `base_chart_data.rb`** — `parse_custom_filters?` calls `filters_schema.call(...).to_h`, which strips undeclared keys, so a new filter is ignored and a CSV export without `skip_pagination` is paginated and truncated. Nullable arrays need `.maybe` (`filled(array[...])` blanks the widget when the frontend sends null, SEN2-383), fixed-choice filters need `included_in?`, date ranges take optional `:date` ends, and declared types match the downstream lookup.
- **Match filter keys end to end, from the registration through the caller to the service** — a service reading `@filter_params[:policy_compliance_*]` while callers send `:induction_compliance_*` silently skips the filter while its specs pass. Add only filter params that `reports_registration/<report>.rb` declares, or the filter is applied but invisible and uncontrollable in the UI. The rule does not apply when the registration changes in the same change.
- **Symbolise `ReportWidgetFile#metadata` filters before passing them to `Csv::V2::Generator` and `ReportInsights` retries** — the stored keys are strings, so `report_widget_file.metadata&.[]('custom_filters')` read as `[:duration_unit]` drops every filter and the export uses defaults; the Tenure and Turnover CSVs showed the wrong unit (RYUK-3677).
- **Convert the `UNASSIGNED_VALUE` (-1) and `UNSPECIFIED_VALUE` sentinels to `nil` once, in the base builder, before any query** — `members.with_teams(@team_ids)` with -1 in the list returns zero rows instead of the members with no team. The rule does not apply to a filter whose `blank_filter` is nil because the downstream service cannot filter unassigned.
- **Treat a value added to a GLOBAL filter mapping as a change to every report that uses it** — adding `DEACTIVATED_OFFBOARDING` to `GetEmploymentStatus` under `EMPLOYMENT_STATUS => { GLOBAL => ... }` mis-filtered sickness V2, assigned learning and 1-on-1 reports, which do not support that status. Add a report-specific filter class or verify every consumer.
- **List a dependent filter in its leading filter's `dependent_filter_names`, declare `STATIC_FILTER_SOURCES` for a new `CUSTOM_REPORT_WIDGET_FILTERS` entry, and set `ui_order` explicitly (global filters -1, content from 1)** — without the dependency `GetData#leading_filters` never passes the parent id, so `CANDIDATE_JOB_RECRUITER` options are unscoped; without the sources the filter shows in the wrong domains; without the order `GetPreviewWidgets` picks the wrong preview.
- **Constrain every one-to-many join to one row per member** — `employment_histories` and `salary_versions` joins need `in_review = false` and a single-row condition, PEO membership is an `EXISTS` rather than a bare `LEFT JOIN peo_connections`, and a table widget must not re-join a table `member_filter` already joins (the Turnover `employment_histories` and Probation `member_managers` joins). A duplicate join inflates counts silently, and `.distinct` on an ordered scope raises `PG::InvalidColumnReference`.
- **Key a UNION or polymorphic match on (type, id), and project the same table's id from every UNION arm** — mixing `sp[:policy_id].as("id")` with `c[:id]` in `CustomReports::Query::PolicyCompliance` attaches the wrong name or status to a document, acknowledgement matching needs `Acknowledgement::POLICY_ITEM_TYPES.include?(a.item_type)`, and `LeaveRequest.leave_category_id` is a `PayCategory.id` in MYOB organisations, so constrain it by payroll.
- **Append a unique tiebreaker to every paginated report `ORDER BY`, and fail or log when a hard cap is reached** — `order("#{sort_first_name} ASC, members.last_name ASC, timesheet_entries.date ASC")` duplicated and skipped rows across pages (DNM-2869) until `timesheet_entries.id` was appended; offset paging over gRPC ordered by `created_at` has the same defect, and `MAX_ROSTERED_SHIFTS` stopping silently at 16,384 rows produced wrong lateness CSVs (EP-5817). In services that `sort.prepend("r_")`, the SQL aliases carry the `r_` prefix.
- **Write report SQL for the null cases** — tenure uses `COALESCE(members.termination_date, CURRENT_DATE)` or it is NULL for every active member, a full name uses `NULLIF(CONCAT(a,' ',b),' ')` because `CONCAT` of NULLs returns a truthy `' '`, headcount denominators use `.active.not_system.not_terminated`, and an account email uses `Member#company_or_account_email` rather than `users.email AS account_email` (EX-2676).
- **Check every caller before adding a pagination limit to a report endpoint** — POKEDIA-4575 was a P1 caused by a caller sending `page: 0`, and it is the reason `EhCop/GrapePaginationMissingLimits` exists; a new `page_index` bound that a live caller violates breaks that caller.

## Exports, jobs and performance

- **Run each heavy report query once per request** — `raw_report_data` and `build_data` both calling `Timesheets::TimesheetReport.run` doubles database load, so the CSV datasource delegates to `GetTableData#raw_report_data`. Calling `.any?`, `.pluck` and `.to_a` separately on a CTE or LATERAL relation re-runs it each time, `@report_data.to_a.size` loads the set to count it (use `page(nil).total_count` or `COUNT(*) OVER()`), `@x ||= policy.check?` re-evaluates a false result (use the `defined?` pattern), and `ReportWidgetFile` rows for a list are preloaded once with `index_by(&:report_widget_id)`.
- **Register a heavy widget in both `ReportWidgets::Fetcher::WIDGETS_READING_FROM_REPLICA` and `Csv::V2::Generator::DATASOURCES_READING_FROM_REPLICA`, and wrap every query of a raw-SQL chart service in `DatabaseReplica.with_read_slaves`** — a widget listed in only one reads the primary on the other path. Bound a slow query with `SET LOCAL statement_timeout` inside a transaction and rescue `ActiveRecord::QueryCanceled`, never with `Timeout.timeout`, which interrupts a pooled connection mid-query and returns it corrupted.
- **Time-bound the `in_progress` file reuse in `ReportWidgets::CreateFile`** — reusing any `in_progress` file forever means one crashed export blocks every later export of that widget for that member.
- **Check the exporter and the widget permission on CSV polling** — `GET ':id/csv_polling/:report_widget_file_id'` needs `exporter == current_member`, the `POST` runs the same `authorized_to_access_widget?` check as widget data, and `ReportWidgetFileWorker` loads through `ReportWidgetFile.in_progress.where(exporter_id:).find_by(id:)` and returns when blank. Otherwise one member downloads another's export, which was filtered with the other member's permissions, and Sidekiq retries pointlessly on deleted rows.
- **Merge fixed pagination keys last, as `@filters.merge(skip_pagination: false, page_index:, item_per_page:)`** — the reversed merge lets a caller's filter hash override the page the export or insight job meant to read.
- **Enqueue `ReportInsights::ProcessReportInsightWorker.perform_async` after commit** — an enqueue inside the transaction runs the worker against a row that does not exist yet, or never will.
- **Set a streamed CSV's headers with `header(k, v)` in Grape `Streamable::Base`** — `response.headers[]=` is a no-op there, so the download keeps the default filename.
- **Keep synchronous payroll-provider fetches off the report dashboard** — a KeypayFetch inside `Members::WidgetsDataAvailability::Payslips` repeats PIP-1238, where cross-region latency and 429s degraded the dashboard.
- **Ship a report backfill as a batched rake task with a per-record `update!`, not `update_all` under an `AuditHero/BulkTrackRequired` disable** — the bulk write loses the SAP audit trail and locks the table across migrations of about 314k rows.
- **Escape a CSV cell that starts with `=`, `+`, `-` or `@`** — free-text fields such as expense details become spreadsheet formulas in an unescaped export.
- **Report a reports-service worker failure once** — `BugReporter.notify` before a re-raise double-reports, because `SidekiqDeathHandler` already reports exhausted jobs; raise `SidekiqSafeRetry` for a retryable error. A long replay triggered from a Kafka consumer (`Payroll::ReleaseHeldRecords.call(...)` in `lib/kafka_registrations/organisation.rb`) is enqueued as a Sidekiq job with JSON-safe arguments rather than run inline, where it blocks the consumer.
- **Map a `PG::QueryCanceled` statement timeout on `ExecuteQuery` to `DeadlineExceededError` with an actionable message** — returning `InternalError` with the raw PG text gives the caller nothing to act on and leaks SQL.
- **Log ids only, never message contents, filter values or SQL with literals, in reports-service consumers, query-engine errors, and backfill logs** — those payloads carry personal and pay data, and an error report copies it into the error tracker and the log store.
- **Return an error rather than a partial result that looks complete when a gRPC call to the main app fails** — an uncaught network error crashes the request, and a swallowed one returns a short report the viewer cannot tell from a complete one.
- **Index a new lookup on a busy topic in the same migration that adds it** — held-record lookups on `member_source_id`, `(organisation_id, hr_member_id)` and `held_since` scan the whole table on every message of the member topic, one of the busiest; a composite `(reason, held_since)` index is not used by a filter on `held_since` alone. Ask for EXPLAIN output on a new complex report filter such as `LeaveDateRange`.
- **Keep high-volume reports-service metrics untagged by organisation, and send 0 for a gauge group that has cleared** — an `organisation` tag on `stale_skipped` or `consumer_failure` creates one custom metric per organisation, and a gauge sent only for groups that still have rows never returns to 0, so its monitor never recovers.

## Custom reports (BYOR)

Build-your-own reports, also called custom reports, span all three codebases: the definition, sharing and permissions live in the main app (`CustomReport`, `CustomReports::*`, the `custom_reports` and `custom_report_files` APIs), the data is served by reports-service (`custom_reports/*` preview, search, distinct values, saved filters and files, the `Query::*` modules and the V1 and V2 engines), and the builder is the frontend canvas (`modules/reports/components/ReportCanvas/`). A BYOR change usually has a counterpart on another layer, so read the subsection for each layer the change touches and check the counterpart exists. Field and row access, tenant scoping and exports rules above apply to BYOR as well.

### Definition, sharing and upgrade in the main app

- **Answer "can this member open this custom report" with one predicate on every path: ownership by `custom_reports.member_id`, or `CustomReport#shared_with?` behind `ff_build_your_own_report_sharing_enabled?`** — the paths disagree, and each disagreement lets a member export a report they cannot view or the reverse: reports-service `FilesController#accessible_reports` also admits `.or(reports.where(creator_source_id: ...))`, and because `DashboardReports::TransferOwnership` moves `custom_reports.member_id` and `dashboard_reports.creator_id` but leaves `custom_reports.creator_id` on the original author, that author keeps export access after a transfer; the main-app `custom_report_files` honours shares without the sharing flag while `GetCustomReportWidgetDataHandler#owned_by_or_shared_with?` requires it; and reports-service resolves TEAM shares from `Dim::TeamMember.active` where the main app uses `member.team_ids`. Treat `custom_reports.creator_id` as attribution only. The rule does not apply where a written product decision keeps creator access.
- **Find shared reports only through `CustomReportShare.shared_with(member)` or `CustomReports::GetSharedReports`** — the scope returns `none` unless `eligible_for_shared_reports?` holds (an active admin or owner, or `BuildYourOwnReportPolicy#access?`), because a share deliberately grants no BYOR permission. A hand-written `CustomReportShare.where(resource_type: MEMBER, resource_id: member.id)` lets a member whose custom-report permission was revoked keep opening shared reports, and misses TEAM and PUBLIC shares. The rule does not apply to admin tooling that lists shares without granting access.
- **Derive a report's share visibility from all of its `custom_report_shares`, never from `custom_report_shares.first`** — `CustomReport#visibility_for_share` reading the first row shows "some" or "public" by row order for a report with both a PUBLIC and a TEAM share; apply the precedence PUBLIC, then some, then private. The rule does not apply if create and update enforce one `resource_type` per report.
- **Find the custom report behind a dashboard report through one helper keyed on `dashboard_report.custom_report_id`** — re-deriving it from the first `ReportWidget::CUSTOM_REPORT` widget's `metadata['custom_report_id']`, as the shares endpoint and `CustomReportFileWorker#dashboard_report` (`.where("metadata->>'custom_report_id' = ?", ...).first`) do, picks an arbitrary widget when there are several and drifts from `DashboardReports::Update#find_custom_report`.
- **Flip `is_legacy` in the same write as a successful save, never in a follow-up `update_columns`** — an `attempt_upgrade` that ran `update_columns(is_legacy: false)` after `custom_report.update` failed marked the report upgraded while the user's changes were dropped; pass `is_legacy:` inside the `CustomReports::Update` params.
- **Keep "upgrade validator unavailable" separate from "report incompatible" in `DashboardReports::Update#resolve_upgrade_eligibility`** — `UpgradeValidator` adds "Failed to validate report against new engine" on a gRPC failure and `Update` returns before its transaction, so with `reports_detail_grain_query` on, a reports-service outage blocks every custom-report save, renames included. On a validator failure, save with `is_legacy` unchanged and log it. The rule does not apply if product has decided saves must block.
- **Raise on a nil `organisation_id` in an organisation-scoped BYOR worker or rake task, and state in the task when it deliberately runs across every organisation** — `CustomReports::StampLegacyWorker#perform(params = {})` enqueued without an id builds `WHERE members.organisation_id IS NULL` and stamps nothing, while reporting success.
- **Back `widget.report_widget_filters.find_or_initialize_by(name:)` in `CustomReportWidgetFiltersSyncable` with a unique index on `(report_widget_id, name)`** — a check-then-write with no constraint creates duplicate filter rows when two saves race, and the filter renders twice. The rule does not apply once the index exists.
- **Never key the `CustomReport` permitted-fields cache on `requester&.id`** — `@permitted_fields_cache[requester&.id] ||= ...` gives every nil requester the shared `nil` key, so one caller's permitted fields are served to another (SEVEN-1889). Require a non-nil requester.
- **Pass the viewer as `current_member` and the row's person as `member` in a report `AuthContext`** — `AuthContext.new(member: member, current_member: member)` in `CustomReports::Query::Helper` decides `WorkEligibilityPolicy#show_visa_details_from_vevo_check?` for the wrong person, so visa fields show or hide based on the employee rather than the viewer.
- **Require `resource_id == organisation.id` on a PUBLIC `CustomReportShare` row, and update shares by diff** — an unchecked target lets a share point at another organisation, and `custom_report_shares.each(&:destroy!)` followed by a full recreate on every update churns rows that a partial unique index should protect.
- **Call `lock!` on the `CustomReport` before reading `member_id` in `DashboardReports::TransferOwnership`** — concurrent transfers otherwise read a stale previous owner, so the audit event and the notification name the wrong person.
- **Let `CustomReportDuplicator` fail through `add_error` and a rolled-back transaction, not a broad `rescue StandardError`** — the rescue swallows programming errors and leaves a dashboard cloned without its custom report.
- **Copy every new `custom_reports` column in `DashboardReports::Duplicate::CustomReportDuplicator` and publish it in `custom_report_message.rb`** — `grain_config`, `anchor_module` and `is_standard` each had to be added to both, because a duplicate silently loses the setting and reports-service never sees the column. The rule does not apply to a purely local or derived column.
- **Keep `is_legacy: @upgrade_to_non_legacy ? false : nil` in `DashboardReports::Update`** — copying create's `resolve_is_legacy` into update writes `is_legacy: true` on every save made while the flag is off, silently reverting V2 reports to legacy.
- **Assign `CustomReport#fields` instead of mutating it in place** — the attribute has a custom getter, so `report.fields.reject! { ... }; report.save!` saves nothing and a data migration reports success while the old field sources stay. Write `report.fields = report.fields.reject { ... }`.
- **Run `fields_too_complex?` and `valid_fields?` in `CustomReports::Update` only when `@params.key?(:fields)`** — unguarded, a rename-only update of an over-threshold report raises `NoMethodError` or is refused.
- **Migrate saved reports, or prove none use the field, before renaming a `has_field` in `CustomReports::Query::*`** — `compliance_status` renamed to `induction_compliance_status` breaks every saved report whose `selected_fields` names the old key. The rule does not apply to a module that never shipped.

### Fields, routing and exports in the main app

- **Hand reports-service the requester's permitted fields, `custom_report.permitted_fields(requester)`, not `selected_fields`, from `CustomReportFileWorker#delegate_to_reports_service`** — `selected_fields: @custom_report.selected_fields.map(&:alias_name)` sends every field the owner picked, and `PermittedFieldsResolver` applies only the `field.permission` lambdas, never `MODULES_TO_PERMISSION_KEYS`, so a shared viewer or an owner whose module permission was revoked exports bank, pay or tax columns on the reports-service path while the main-app export (`CustomReports::Export#selected_fields`) and the table (`GetCustomReportWidgetDataHandler`'s `permitted_field_aliases`) hide them. The rule does not apply once reports-service resolves module permission keys for the requester itself.
- **Fail the export when the requester is missing, and never fall back to the report owner** — `requester_id ? Member.find_by(id: requester_id) : custom_report.member` in `CustomReports::Export#requester`, and `CustomReport#context(requester = nil)` building `AuthContext.new(current_member: member)`, evaluate field permissions and `has_field` lambdas as the owner, so a file whose metadata lost its requester exports with the owner's wider access. The rule does not apply to report types and standard reports, which have no viewer.
- **List every one-to-many query module in both `CustomReport::ONE_TO_MANY_MODULES` and reports-service `CustomReports::CreateFile::ONE_TO_MANY_MODULES`, key `CUSTOM_REPORT_EXPORT_COMPLEXITY_BYPASS_IDS` the same way on both sides, and keep `custom_reports.errors.export_too_complex` worded to match the check** — `too_complex_for_export?` counts only the listed modules, so a new event module missing from a list never trips the five-module cap (EX-3263) and the export runs out of memory again. The copies have drifted already: `Expense` is in the reports-service list only, the main app matches bypass ids on `id` while reports-service matches `source_id`, and the message still mentions 100 fields the check no longer tests.
- **Exempt a report from the export complexity cap only through `CUSTOM_REPORT_EXPORT_COMPLEXITY_BYPASS_IDS`, never with a caller-level `bypass_complexity_check: true`** — `CustomReports::CreateFile.new(custom_report: custom_report, bypass_complexity_check: true)` in `Reviews::Reports::CreateFile` exempted every performance-review export, including the ones that multiply rows, which is the memory exhaustion the cap exists to stop.
- **Register a new query module in `CustomReport::NAME_TO_MODULE`, and resolve any module outside it explicitly in `canvas_selected_fields`** — canvas mode resolves stored fields against `NAME_TO_MODULE.values.flat_map(&:fields)` and `.compact`s whatever it cannot find, so `EmployeeFileCustomField` columns vanished until they were added explicitly (EX-3306); check the `SPECIFIC_REVIEW_PERIOD_NAMES` modules (`PerformanceReviewAnswers*`, `PerformanceReviewReviewers`) when a legacy report using them opens on the canvas. The rule does not apply to a module product never offers on the canvas.
- **Keep the module names in `CustomReports::Domains::SOURCES` identical to the names stored in existing `custom_reports.fields`** — the module string is a persisted key, so a canvas `/sources` name that differs from the stored `TaxAndNI` stops legacy reports resolving their fields.
- **Mirror every change to a main-app `CustomReports::Query::*` module or `CustomReports::Query::PreviewBuilder` into its reports-service `Query::*` counterpart, and link the counterpart change** — both engines serve BYOR until the migration ends, so a sort guard, a label rename or a new field changed on one side shows different data depending on which path the report takes (a `sortable: true` drift on `employment_type` is the known case).
- **Set `rs_source: true` on a main-app `has_field` only when reports-service has a field with the same alias, data type and sortability, and assign `rs_source` in `Field#initialize`** — one such field (`selected_fields.any?(&:rs_source)`) routes the whole report's table, search and export to reports-service under `byor_reports_service_routing`, and an attribute declared but never initialised leaves the routing unreachable.
- **Add a new custom-report export filter to both the main-app `custom_report_files` Grape params and reports-service `CustomReports::CreateFile::FILTER_PARAM_KEYS`** — reports-service builds the export payload from that allow-list, so a filter missing from it exports unfiltered on the reports-service path while the main-app path filters.
- **List every source-specific BYOR filter in the source map of `ReportWidgetFilters::CustomReport::FilterAvailability`, and test both outcomes** — `MergeByorFilters` decides from that map whether a table filter shows, so a missing entry shows a filter on reports without its source or hides it on reports that have it; test "source selected, shown" and "not selected, hidden".
- **Declare a main-app `CustomReports::Query` field's `data_type` to match the value it renders** — a leave balance formatted to two decimals but declared `DATA_TYPE_FLOAT` is parsed back to a float, dropping trailing zeros and restoring long decimals, and `DATA_TYPE_BOOLEAN` renders "Yes" and "No" by default.
- **Derive BYOR `has_field` values in SQL or through a narrow `includes:`, not in a Ruby block that loads associations per row** — `source: ::LeaveRequest do |lr| ...approvals.select(&:approved?).map {...} end` loads approvals row by row inside `CustomReportFileWorker` and repeatedly exhausted memory on the Medium Sidekiq queue, and `members.select { policy(m).has_custom_report_permission? }` before `.page` hung staging in `CustomReports::EligibleOwners`. The rule does not apply to a cheap scalar read on an already loaded record.
- **Make a main-app BYOR field return the value that is published for it** — `cms_cycle&.pay_effective_from` in the query module and a different value in the decorator show different numbers on the main-app and reports-service paths of the same report.

### Reports-service custom report API

- **Gate a sensitive reports-service field in `PermittedFieldsResolver` through its `field.permission` lambda, and never assume that `FieldAccessPolicy`, `FieldPermissionChecker` or `BY_MODULE` protects a saved report's search, view or export** — those three run only on `ExecuteQuery`, so a new pay, tax, bank or personal field left on the default `->(_context) { true }` lambda, or gated only by a flag or a country, is visible in the table and the CSV to every holder of the reporting permission. The rule does not apply to code reachable only through `ExecuteQuery`, or to the Compensation reports that `Reports::CompensationReportPolicy` already gates.
- **Raise when the visible-member list cannot be resolved, and never return `[]`** — an empty list means "sees nobody", so a `BuildYourOwnReportPolicy` paging failure that returns `[]` produces a silently empty report. Raise `VisibleMembersUnavailableError`, bound the paging by wall-clock time, and detect a cursor that stops advancing. Do not stack the reporting-line filter (`manager_scoped_byor`) on top of a visible-member scope either: a location manager with no direct reports then sees zero rows.
- **Write the organisation-level saved filter (`member_id: nil`) only for a member who can edit the report** — with `custom_report_builder_canvas` on, `Members::Reports::SavedFiltersController#upsert` and `#destroy` pass `shared_filters: true` after checking only `dashboard_reports_policy.access?`, so any viewer of a shared report overwrites or deletes the filter every other viewer sees, and the frontend's `permissions.can_save_filters` is the only guard. The rule does not apply to STATIC reports, whose organisation-level storage predates the canvas.
- **Enforce advanced-filter limits in the validator every entry point calls, not only in the request's Dry schema** — saved filters, the gRPC export and the preview and search params all reach `AdvancedFilter`, so a limit that lives only in `Query::AdvancedFiltersSchema` (`MAX_ROOT_RULES = 20`) is skipped for a stored or gRPC-supplied tree.
- **Return `TabularResult` and builder validation errors as a 4xx from `CustomReports::Preview` and `Search`** — `Preview#build_data` ignoring `tabular.errors` returned `{items: null}` with status 200, and an invalid `module_operator` raised `ArgumentError` as a 500 until `preview_controller` mapped it to 400.
- **Forward every report-definition attribute that preview and search read through the whole export chain** — `anchor_module`, `module_operator_json`, `grain_config_json`, `is_legacy` and `advanced_filters` travel the gRPC proto → `StartCustomReportExportHandler` / `CreateFile#export_payload` → `ExportWorker#run_export` → `Export` / `ExportGrpcResult` → `WidgetDataAdapter`. A missing one raised `GRAIN_STRATEGY_CLASS.fetch(nil)` → `KeyError`, swallowed as `status: "error"` (EX-3311), exported legacy reports through V2 (EX-3416), and exported unfiltered data under a filtered UI. Keep a fallback for jobs already queued, because their Sidekiq payloads lack the new key.
- **Read the report-level saved filter in export with `report.saved_filters.find_by(member_id: nil)`, and fail the export when the stored advanced-filter tree fails `Query::AdvancedFiltersSchema`** — the organisation-level filter is stored with the report, not with each viewer, and an invalid tree that falls through exports unfiltered data.
- **Put a new hard failure in the export path behind the export flag** — `return fail_unresolved_aliases if unresolved_aliases.any?` without `byor_migration_export_csv` makes existing exports start failing for every organisation at deploy.
- **Page a reports-service export with `Query::ReportBuilder::ExportBuilder`'s `DECLARE … NO SCROLL CURSOR WITH HOLD` and `FETCH FORWARD`, pass `configurations[:cursor_name]`, and close the cursor in the caller** — LIMIT/OFFSET paging skips or duplicates rows when data changes between pages and re-runs the query on every page, and an unclosed held cursor leaks. The rule does not apply to preview or search pagination.

### Reports-service query modules

- **Do not give a module whose fields are all `field_type: FIELD_TYPE_DERIVED` a joined `table_key` in `ModuleRegistry` or `with_table`** — derived values come from `includes:`, so the join only multiplies rows: a member with N custom-field values appears N times and other members drop out (EX-3306). The rule does not apply when the module also has SQL-selected fields that need the table.
- **Declare `data_type` to match the Postgres column** — `dim_members.member_id` declared `DATA_TYPE_STRING` offers `contains`, `starts_with` and `is_blank`, which generate `ILIKE` or `= ''` on an integer and fail, and hides the numeric operators; date columns declared as strings cannot be filtered before, after or between and sort as text. The rule does not apply to a computed display string.
- **Declare `has_field :id, identity: true` as `DATA_TYPE_STRING`** — the id is a UUID, `DATA_TYPE_INTEGER` coerces it to `0` with `.to_i`, and because derived-field preloading is keyed by id, every derived field in the module renders blank (EX-3308).
- **Give every `has_field` `alias_prefix: :<main-app table name>`, and never register the same field name twice in a module** — without the prefix the alias is built from `Fact::X.table_name`, does not match the gRPC `selected_fields` alias, and the field is dropped from results; two registrations with different `alias_prefix`, `sortable` or `rs_source` collide on one alias, and whichever loads last wins. The rule does not apply to a module-local hidden helper field.
- **Read a derived field through an `active_dim_<assoc>` association declared `-> { where(deleted_at: nil) }`, never the raw `dim_<assoc>`** — the raw association shows names and categories from soft-deleted dim rows (PEAC-4377). The rule does not apply when the report is meant to show historical labels.
- **Join a fact table through `current_state` (`scope: :current_state` in V1 `with_table`, `.current_state` in a V2 `subquery`)** — a raw `fact_*` table returns one row per historical version of each `source_id`, so every member appears once per version.
- **Compute a migrated field from the main app's definition, not from a stored column of the same name, and ask for the main-app source line in the change** — `leave_requests_total_units` reading `total_units` returned NULL on 30 of 50 rows where the main app reports `hours? ? total_hours : total_units`, and a review progress figure has to combine every reviewer. Fix every use of the field, because a fix to the display value leaves sort, filter and aggregation still reading the raw column (`days_per_week`, which defaults to 5, also feeds the day-rate salary sort). The rule does not apply to a new field with no main-app counterpart.
- **Guard a `Date.current`-relative derived field against past and future dates inside the field, and apply the same guard to its SQL sort expression** — the main app filters rows (`active_probation_condition_sql`) before computing such a status and `has_field` has no row filter, so `if end_date <= Date.current + PROBATION_ENDING_SOON_DAYS.days` labels ended probations "Ending soon" forever, and `calc.call(from, Date.current)` returns negative durations for future termination dates. Evaluate "today" per call: memoising it in a constant, or pre-materialising a date-relative "current" record, picks the wrong record once the date changes.
- **Add a `query.field.<module>.<name>` entry to `config/locales/en-AU.yml` and the other locales for every new `has_field` without a `:label`, in the main app's wording** — `Field#default_label` builds the key from the class name, so a missing entry renders "translation missing" as a column header.
- **Prefix ActiveRecord constants with `::` inside a `join_conditions` lambda in `module Query`** — a bare `LeaveRequest`, `MemberLicence` or `SalaryVersion` resolves to the plain class `Query::LeaveRequest` and raises `NoMethodError` at query-build time, which registry-metadata specs do not catch; specs call every lambda.

### Reports-service V1 and V2 engines and charts

- **Carry every V1 `join_conditions`, `member_fk_col` and filter from `Query::Helper` into the module's `Query::ModuleRegistry` entry** — `member_licences` and `employment_histories` need `member_fk_col: :member_id` or raise `PG::UndefinedColumn member_licences.member_source_id`, MedicalDisclosureStatement needs `in_review: false`, Certification needs `archived_at IS NULL`, and views need the organisation filter (EX-3302). The rule does not apply to a module that exists only in V2.
- **Allow at most one one-to-many module to multiply rows, the anchor, and collapse every other one-to-many module to one row per member** — chaining direct joins for two one-to-many modules builds a Cartesian product that inflates COUNT, SUM and AVG, and an 89-member organisation's export of about 133 fields exhausted the database's memory. Register a collapsible module with a `collapse_strategy`, make only `ONE_TO_MANY_EVENT` and `ONE_TO_MANY_COLLAPSIBLE` modules `anchor_eligible`, never make a `dim_members` module anchor-eligible (`PG::DuplicateAlias`, EX-3304), never reuse a claimed `table_key` (duplicate CTE, EX-3321), and keep every module in `ALL_QUERY_MODULES` in `ENTRIES` or `PERMANENTLY_SKIPPED`. The rule does not apply to the V1 path while its flag is off.
- **Key `module_operator` by module name, not `table_key`** — the main app syncs it and knows nothing of dim and fact tables, so `widget_data.module_operator[entry.table_key.to_s]` silently falls back to `'inner'`.
- **Group by the same expression the select projects** — a select that wraps a group column in `COALESCE(..., 'Unspecified')` while `build` groups on the raw column returns a NULL group and a real `'Unspecified'` group as two rows with one label, splitting the chart's count.
- **Use a group `label` that is one-to-one with its key** — rows group by (key, label), so `job_histories_department → job_histories_job_title` splits one department into several bars with partial counts; specs use a pair such as `members_id → members_first_name`.
- **Do not group by an `identity: true` field without visible column metadata** — `ColumnBuilder#visible_fields` drops identity fields, so `output_columns` raises "group field 'members_id' must have visible column metadata" once the new engine is on.
- **Validate aggregations and options in `GroupedValidator`, and keep BYOR off `QueryEngine::Schema::AGGREGATIONS`** — `distinct` is valid only on `count`, `sum` and `avg` only on numbers, and `grand_total` only as a boolean; an error raised later from a memoised strategy becomes a 500 instead of `invalid_grain_config`. The aggregation list belongs to HeroAI, so sharing it lets a HeroAI change alter BYOR.
- **Reject an unknown `time_zone` on a time-grained `group_by`, and check that the field is a date or time** — falling back to UTC or an AU zone groups periods in the wrong zone for UK, NZ and Asia customers with no error (SEVEN-2349). A blank zone may default to UTC, and known short names normalise (`'Sydney'` → `'Australia/Sydney'`).
- **Make a masking or permission hook fail loudly when it cannot apply** — `SensitiveLeave::MaskingConcern` works only while it sits before `QueryExecution` in the ancestor chain, so reordering includes disables masking silently without a boot-time ancestors assertion, and `next unless k.start_with?(eh_prefix)` on a drifted key skips the field unmasked. Mask on all three BYOR paths: V1 `PreviewBuilder`, V2 `BaseBuilder`, and the CSV export (BOBA-282, BOBA-283).
- **Decide a permission or engine gate on the backend, and put the cheap local check first** — trusting `optional(:is_new_engine).filled(:bool)` from the client lets a caller pick the engine; check `reports_detail_grain_query` server-side as `!@widget_data.is_legacy? && policy.ff_...?`, because the flag lookup may call gRPC. Authorisation, such as filtering inaccessible metrics, belongs in the controller or handler.
- **Cache a permission RPC result under organisation + member + the requested field set with a short TTL, cache both outcomes, and fall straight back to the live call on a Redis failure** — `cache_result if @use_cache && allowed` re-asks for every denial, and a retry sleep or a per-request error report on Redis failure turns a cache outage into a slow report. Do not use the cached BYOR context (300s) for 2FA enforcement on a write path; `files#create` takes a fresh fetch (SEVEN-2337).
- **Qualify a custom chart's GROUP BY and SUM with a table its `query_scope` actually joins** — `CustomCharts::SingleFieldChart::View#field_source` and `#field_metric_source` switch to `star_schema_source` under `reports_star_schema_query` while `#query_scope` still builds its joins from the association, and six chart fields failed with `PG::UndefinedTable: missing FROM-clause entry for table "fact_employment_histories"`.

### Frontend canvas

- **Send `advancedFilters` to `/search` and `/preview` only when the group has rules** — `...(isRSCustomTable && advancedFilters != null ? { advancedFilters } : {})` in `useReportWidgetDetails` or `usePreviewCustomReportTable` also sends `{ conjunction, rules: [] }`, which `ReportCanvasExportMenu` treats as unfiltered while the API receives a group, so the export's "filtered" label and the data disagree. Gate on `(advancedFilters?.rules?.length ?? 0) > 0` (`hasAdvancedFilterRules`), unless the producer provably emits `null` for zero rules.
- **Send an explicit `null` when the user clears a saved filter** — `...(advanced_filters != null ? { advanced_filters } : {})` in `useUpsertSavedFilters`, or in any `buildReportCanvasPayload` field, drops the key, and on a merging backend the old personal `saved_filter.advanced_filters` survives and wins over the report's filter on reload. Use `!== undefined`, unless the change links backend confirmation of full-replace semantics.
- **Derive one `hasActiveFilters` value that counts basic and advanced filters, and use it everywhere "any filter active" is asked** — checking `Object.keys(filterValues).length === 0` in `willClearSavedFilterOnSave`, `persistFiltersAfterSave` or the `PreviewDataTable` empty state fires the clear-saved-filter popup and `deleteSavedFilters` while an advanced filter is still set. A new filter type added to one of those checks and not the others is the finding.
- **Reset pagination to page 1 on every filter change** — wiring `onAdvancedFilterChange={setAdvancedFilterGroup}` without `setPreviewFieldSelection(c => ({ ...c, page: 1 }))` refetches at the current page, so a user on page 3 who narrows the filter gets an empty or wrong page. Route every filter change through one handler such as `handleAdvancedFilterChange`.
- **State what happens for a viewer without `permissions.can_save_filters`** — advanced filters persist only in the per-member `saved_filter`, and `persistFiltersAfterSave` returns early without that permission, so the viewer applies a filter, saves, and loses it on reload.
- **Make the parent wait for the data before mounting `NewReportCanvas` with seeded `initial*` props** — `useState(initialAdvancedFilterGroup ?? existingCanvasData?.advancedFilterGroup ?? null)` ignores a value that arrives after mount, so `ExistingReportCanvas` blocks on `savedFilterApi.dataReady` as it does for `initialFilterValues`; without the wait the saved filter is silently missing on a slow network.
- **Reset the UI in `useRememberFilters` only after the saved-filter delete succeeds, and handle `onFailed`** — resetting inside `useDeleteSavedFilters.onComplete` with no `onFailed` leaves the filters unreset and the user unaware; on failure keep `hasSavedFilter` true and show a toast.
- **Keep the filter subtree's shape stable while a flag resolves** — `{isAdvancedFilterEnabled ? <div ref={filtersRef}>{filtersNode}</div> : filtersNode}` remounts `ReportCanvasFilters` and `AnchorSelector` when `useCheckFeatureFlag` resolves, losing dropdown state and repeating `filter_metadata` fetches.
- **Format each date filter in its own wire format** — advanced rule values are ISO `YYYY-MM-DD` from a native date input and use `formatDateLocalized`, basic filter values are `LEGACY_INTERNAL_DATE_FORMAT` (`DD/MM/YYYY`) through `formatDateForDisplay`, and crossing them swaps day and month in the filter chips. Specs assert the exact string (`31/12/2020`), not `toContain('2020')`.
- **Offer operators per `data_type` from `getOperatorsForDataType`, with before and after wording for dates** — `gt`, `lt`, `gte` and `lte` labelled "is more than" or "is at least" read wrongly on a date, and `lte` beside `before` (`<=` against `<`) is ambiguous. Adding a generic comparison operator to the date set needs PO sign-off.
- **Read the date-range limit from typed filter metadata (`item.metadata?.max_days`) and bound the picker as `{ maxDate: new Date(), minDate: subDays(new Date(), maxDays - 1) }`, with a test that selects a real out-of-range date** — an off-by-one lets users pick a date the backend rejects, and a test that only checks the prop is passed cannot see it.
- **Separate whether `TopBar`'s Save button renders from whether it is enabled** — `{(isNewReport || (canEdit && (hasUnsavedChanges || canSave))) && ...}` hides the button and its "Add a report name and at least one field" tooltip for a legacy report with an `upgradeBanner` and validation errors; render on `hasUnsavedChanges || hasUpgradeBanner` and set `disabled={!canSave || isReportBusy}`.
- **Branch a canvas save failure on the error** — `onFailed: handleSaveFailed` that ignores its argument shows the persistent "too many data sources" banner for every 500, network or permission failure, beside `useApi`'s own toast. Prefer a structured `reason`, as `isUnauthorizedFieldsError` reads `reason === 'unauthorized_fields'`, and match message text only through a named constant such as `MODULE_LIMIT_ERROR_MESSAGE_FRAGMENT`.
- **Render `WidgetPermissionErrorState` before the generic `WidgetErrorState`, and pass `isUnauthorizedFieldsError` a typed `UnauthorizedFieldsErrorBody | null | undefined`** — a cast such as `(previewQuery.error as {...})?.body as UnauthorizedFieldsErrorBody` hides the undefined case, and a viewer with restricted fields sees a generic error instead of a no-access message.
- **Reset a refresh flag set before a fetch in that fetch's failure path** — `isPostSaveRefreshRef.current = true` in `onUpdateComplete`, cleared only on success, stays set when the refetch fails, so the next real refetch skips the `canvasVersion` bump and shows stale data.
- **Keep state updaters pure in the canvas** — `setSavedSnapshot(...)` called inside `setSelectedFields(current => { ... })` runs twice under StrictMode and couples the saved snapshot to updater timing, which breaks unsaved-change detection; compute `nextFields` outside and call both setters.
- **Memoise legacy wizard conversion above the early returns, and return `null` for an unknown operator** — `isOldWizardReport(t) ? convertOldWizardReport(t) : ...` outside a `useMemo` reconverts on every render, a throw caught by `try/catch` hides which operator failed, and `'with'` and `'with_or_without'` belong in the `LEGACY_OPERATOR_*` constants. Warnings derived from `existingCanvasData` describe the import snapshot, not live state.
- **Prove that the anchor invariant cannot block the new-report flow mid-build** — `hasUncollapsibleWithoutAnchor = anchorModule === null && selectedSources.some(isNonCollapsibleSource)` disables save and preview, and `resolveAnchorModule` auto-anchors only a lone non-collapsible source; a legacy anchor leaking into `/preview` is the related defect (SEVEN-2161, SEVEN-2275).
- **Take the field cap from `MAX_SELECTED_DATA_POINTS` in both the message and the guards** — a hard-coded "up to 50 data points" drifts from the constant, and single-add (`>= MAX`) and bulk (`+ n > MAX`) guards that disagree make the cap bypassable. Re-ensure First and Last name through `ensureRequiredFields` on every source entry.
- **Keep identity separate from edit permission in canvas props** — `isOwner` compares the current owner — `custom_reports.member_id`, or the dashboard report's `creator_id`, both of which move on transfer — with `currentMemberId`, never `custom_reports.creator_id`, which stays on the original author; and it is not `!readOnly` (which comes from `permissions.editable`), and conflating them breaks owner-only gating such as ownership transfer (SEVEN-2302) and the analytics `is_owner` property. Group the `canDelete`, `canEdit`, `canSave` props into one `permissions` object, with `canDeleteReport` from `customReport.permissions.delete`.
- **Initialise multi-source tracking after the catalogue loads** — `useRef(initialActiveSourceCount >= 2)` is evaluated while `availableCatalogue` is empty, so an existing multi-source report emits a false "State Custom Report Multisource" event when a third source is added.
- **Export only the last saved canvas, and show the unsaved-changes notice when `hasUnsavedChanges && savedReportExport`** — an export path that reads unsaved canvas state exports something the user never saved (SEVEN-2282, EX-3333). A change that threads a filter into the PDF says what the CSV does.
- **Fire BYOR analytics events through `trackMixPanel`, once per user action, with every property defined** — a show-modal event fired from an effect fires twice under StrictMode, a new report sends `report_id: undefined` until its first save, and `trackConversionFailed` sends `failure_reason: undefined` when `isPartialState` is true without a reason; each skews the funnel.

## Sync from source services

- **Republish explicitly after any write to a synced model that bypasses `after_commit`** — `update_all`, `delete_all`, `delete`, `insert_all`, `upsert_all` and raw SQL never reach `ReportsData::CallbackHandler::BUSES_MAPPER` or a `KafkaHandleEvent.register … live_sync` watch, so reports-service drifts silently. Re-query updated rows by captured ids, load rows before deleting them, and call `ReportsData::CallbackHandler.new(Model, :update/:destroy, record).call`; deletes matter most, because the backfill never replays them and the orphan stays. The rule does not apply to a model not registered for reports sync.
- **Publish after commit, and never let a publish failure raise into the user's transaction** — publishing from `before_*` or `after_save` sends rows that later roll back, and a Kafka error that propagates fails the user's save. The rule does not apply to an outbox implementation whose write shares the transaction.
- **Send UUIDs for the message root `uuid` and for `organisation_id` and `member_id` in `data`, and backfill uuids before enabling a publisher** — an integer key leaves `source_id` null, a .NET source sending the wrong organisation id breaks tenant isolation, and a null `object.uuid` produces rows nothing can update later.
- **Add a new synced column in all four places at once: the source decorator, the reports-service `map_column <local>, <kafka_field>`, the write service's `PERMITTED_ATTRIBUTES`, and the catalog `columns`** — a column missing from `PERMITTED_ATTRIBUTES` is dropped silently, `map_column` arguments are easy to reverse, and every column a catalog declares must be mapped: an unmapped fact column is always NULL, so fact tables need `map_column :source_created_at, :created_at`. A field that exists only through a join (`leave_category_name` in `snapshot/leave_requests.yml`) does not belong in the catalog.
- **Emit raw columns from a main-app reports decorator, using `object[:col]` where a computed method shares the column's name** — the computed method bakes main-app business logic into the reporting copy, and the reporting field then disagrees with every path that applies that logic itself.
- **Compute a derived value identically in the live serializer (`do_serialize` or the decorator) and the backfill serializer (`do_serialize_record`), with the same `topic_type`** — live and backfilled rows otherwise disagree, and a mismatched `topic_type` routes backfill rows to the wrong handler.
- **Preload every association a reports decorator reads in both `CallbackHandler::BUSES_MAPPER` (`association_preload`) and `SyncDataHandler::MODEL_QUERY_MAPPER`** — `FullTableBackfillHandler` reads only the latter, so a decorator reading `object.organisation&.uuid` or `object.policy&.name` runs one query per row on backfill. Use `.any?` rather than `.exists?` on a preloaded association.
- **Register the dependent model in `BUSES_MAPPER` when a synced field is derived from it** — a field such as `object.documents.any?` stays stale in reports-service until the parent record next changes.
- **Wrap payroll, pay, tax, bank, super, medical, immigration, compensation and timesheet-cost payloads with `KafkaHandleEvent.encrypt(data_payload)`, including `PublishSearchComparison` results** — `PayloadEncryptor#decrypt` passes plaintext through unchanged, so a plain payload works end to end while pay data sits readable in Kafka for the retention window. Encrypt the whole payload, on publisher and consumer. The rule does not apply to operational or configuration topics such as leave, assets, teams, policies, reviews and workflow.
- **Keep nil distinct from 0 in a synced value, and round money as `BigDecimal(x.to_s).round(2)`** — a nil coerced to 0 reports a real zero salary or balance, and float rounding drifts cents between the two report paths.
- **Create the `<Source>.ReportsData.<Entity>` topic in every environment before the publishing code merges** — application code merged ahead of the infrastructure topic publishes into nothing, and the first symptom is that no data arrives.
- **Decide what is synced (for example `current_version`) in the handlers, not in a decorator's `create_message`, and send destroys through `DestroyMessageConcern` with `SyncDestroyEventWorker.perform_in(10.seconds, ...)`** — a decorator that filters makes live and backfill disagree, and an immediate destroy can overtake the last update.
- **Pass `destroy_delay` worker arguments as JSON (`message.to_json`)** — strict Sidekiq arguments reject a hash with symbol keys, so the delayed destroy is never enqueued.
- **Check `success?` and `result` on an `EhProtobuf::Response` and rescue `EhProtobuf::Errors::*`** — the client does not raise `GRPC::BadStatus`, so a rescue for it is dead code and a failed call reads as an empty success.
- **Order a backfill handler's `do_fetch_batch` by its cursor key, compare cursors typed (`id > ?::uuid`, never `id::text`), make partition bounds half-open, set `config.backfill_source_service`, give each service its own consumer group on `Reports.BackfillRequest`, reply `complete` rather than an empty batch, and never re-raise out of the consumer** — each mistake has its own failure: skipped or duplicated rows, a sequential scan instead of the primary-key index, a boundary row read by two partitions, two services answering one request, services stealing each other's requests, and a run that never finishes.

## Reports-service catalog and storage

- **Give every catalog YAML in `config/catalog/**` an `access:` block, closed by default** — a table with no access declaration is denied to everyone including owners, and `default_access: open` on a table holding pay, expense, tax, termination or personal data is a leak. Use `access: { permission_key: security_permissions_*, scope: table }`, add `access_roles: [employer, owner]` to sensitive columns, and give a snapshot or mirror the same access as its fact table. The rule does not apply to a business-settings table with no personal data that the reports-service owners have approved as open.
- **Never drop or rename a live reporting table in the same change that adds its replacement** — `drop_table :dim_policies` empties the report in production until a backfill, coordinated through SAP, has filled the new table. Use the generic backfill rather than a per-table `Backfill::*Worker`, unless the job copies data internal to reports-service.
- **Create each reports-service index in its own migration with `algorithm: :concurrently` and `disable_ddl_transaction!`, add no foreign keys, and keep `db/schema.rb` free of unrelated tables** — an index built in the same migration as a column change locks the table, and an unrelated `schema.rb` diff ships schema drift. Update the catalog table-count spec when the count changes. The rule does not apply to indexes inline in a `create_table` for a new table.
- **Add a `(member_fk_col, tiebreak_col DESC)` composite index to every table used as a `DISTINCT ON (member_fk)` collapse source** — without it every report that collapses the module sorts the whole table.

## Reports-service request context

- **Know which zone `Date.current` resolves to on each reports-service path, and never use `Date.today`** — controllers and `ExportWorker` set the user's or organisation's zone, while gRPC handlers, Kafka consumers and other workers run in UTC, so a `t[:effective_from].lteq(Date.current)` period check in a `ModuleRegistry` subquery flips around 10 to 11am AU time on the gRPC path.
- **Reset `I18n.locale` and `Time.zone` in an `around_action` with `ensure`** — both are thread-local and Puma reuses threads, so an `after_action` reset is skipped when a `before_action` halts or the action raises, and the previous request's locale or zone leaks into the next.

## Reports-service ingest write path

- **Call the `Dim::*UpsertService` alone from a Kafka registration for a `Dim::*` table** — `KafkaRegistrations::ConsumerDataEventHandler.new(model: Dim::X ...)` on a dim table with no separate sync model hard-deletes on destroy (`record.destroy!`), so the soft-delete upsert then finds nothing. The rule does not apply to a true sync table, which runs the consumer handler first and the upsert service after.
- **Apply "newer wins" in one atomic statement: `ON CONFLICT ... DO UPDATE ... WHERE excluded.source_updated_at > t.source_updated_at`** — a `stale?` read followed by an unconditional `upsert(attrs, unique_by: :source_id)` races when the live topic and a replay write the same `source_id`, and a late, older destroy must not delete a newer held update. A `return if stale_event?` inside `super` only leaves `super`, so subclass side effects (`recompute_managers_is_manager`) still run on stale events.
- **Keep `source_updated_at` in change detection, and strip ActiveRecord `updated_at` and `created_at` from backfill attributes** — `EXCLUDED_FROM_DIFF` dropping `source_updated_at` or a backfill overwriting it with the replay time makes later live events look stale, so they are discarded (PEAC-4328).
- **Recompute a relationship-derived value whenever any of its inputs changes** — `dim_members.is_manager` recomputed only on MemberManager events goes stale indefinitely when a member's `is_active`, `termination_date` or `worker_type` changes.

## Feature flags

- **Pass a uuid context to `FeatureFlagAssistant.on?(flag, {organisation:, member:})`, never a model** — `FeatureFlagAssistant.on?(:feature_reports_payroll_employee_details, auth_context.organisation)` does not resolve per-organisation targeting, so the flag reads off for the organisations it was switched on for, and a spec stubbing `.with(flag, anything)` hides it.
- **Define one policy predicate per report flag and use it in the query service, filter options, table columns, and both create and update** — ad-hoc copies drift; one produced V2 filters over V1 columns. Examples are `BuildYourOwnReportPolicy#ff_detail_grain_query_enabled?` and `BackgroundCheckPolicy#zinc_status_v2_enabled?`.
- **Make flag-off behaviour exactly the pre-change behaviour, and re-check flag-gated data when it is rendered** — flag-off returns the old scope (`leave_categories.is_hr.enabled`) and the old menu order, a flag-gated filter param arriving with the flag off is stripped (`params[:custom_filters].delete(:snapshot_date)`) rather than answered with a 422 or 500, flag-gated meta keys are emitted only when on, stored CSV column configs re-check the flag at build time or the columns leak after a rollback, and a new CA payroll report goes in `CA_FEATURE_FLAGS` before `CA_REPORTS`. The rule does not apply once the flag is at 100% and the old path is being deleted.

## Frontend reports module

- **Resolve report flags once in a stable parent and pass the result down** — `useHideCustomReportCharts()` or `useCheckFeatureFlag(...)` inside every `ReportCard`, `ReportWidgetCard`, `WidgetBlock` or `PinReportDetails` issues one flag request per card and again on every tab-switch remount. Resolve in `CardView`, `MyReportsDashboard`, `Details/index.tsx` or `WidgetPinReport/index.tsx` and use the pure `getCustomChartVisibility` inside widgets. Declare a new flag as an `XXX_FEATURE_FLAG` constant in `constants.ts`: the raw `'report_analysis_filtering'` string read separately in `ExistingReportCanvas` and `NewReportCanvas` is two reads that can drift.
- **Model a report flag's loading as its own state, `'checking' | 'hidden' | 'visible'`** — reading only `accessible` from `useCheckFeatureFlag(TRANSFER_OWNERSHIP_FEATURE_FLAG)` makes actions pop in late, and overlapping booleans (`hideCustomCharts`, `isCheckingFlag`, `holdCustomCharts`) show old-builder organisations a placeholder that flickers into a live preview. Use `useReportCanvasFeatureFlag`'s `loading || (!data && !error)` and hold the fetch while checking.
- **Make a hidden or unavailable chart fully inert** — when `isUnavailableChart`, pass no `widgetActions`, fetch neither `/preview` nor `custom_charts/fields` (`shouldHoldChartFetch`), and share one `isWidgetInPdf` predicate between the PDF widget count and the render filter, because a mismatch leaves `onAllWidgetsLoaded` waiting forever. Keep tracking props such as `onChartAdd` wired when the switch flips.
- **Keep `JSON.stringify(fetchParams)` in `useReportWidgetDetails`' fetch dependencies** — `[fetchWidgetDetailsFn, fetchParams, ...]` changes identity every render, fires duplicate `/search` calls, and `WidgetBlock`'s `pdfAccumulatedRowsRef` appends the duplicates, so the PDF export repeats rows. Any change to that array needs a multi-page PDF check.
- **Skip a `dashboard_reports/*` fetch when the id is missing, fetch once, and default `totalPages` to 0** — `endpoint: .../dashboard_reports/${customReportId ?? 0}/...` requests `/dashboard_reports/0`, `useApi(..., [id, pageIndex, itemPerPage])` beside a `useEffect(() => fetchData(), [...])` fetches twice (use `autoFetchWithParams`), and `total_pages ?? 1` shows a phantom page before load.
- **Pass `DefaultReportTable` a stable `customColumnPropsByAccessor`** — an inline object changes every render and is a dependency of the `tableColumns` `useMemo`, so the whole column chain and the large table recompute; use a module-level constant or `useMemo`.
- **Read the HeroForce badge key from that report's backend serializer** — the leave reports send `is_heroforce` and other reports `is_heroforce_employee`, so a mismatched key hides the badge silently. Reuse `EmployeeNameWithHeroForceBadge` or `createHeroForceNameCell` unless the cell branches further.
- **Put report-specific permissions on the row items, not on the shared `ReportServiceWidgetItemMetadata`** — a field such as `can_modify?` on the shared metadata type changes the contract of every report; `DisciplinaryCaseRow.can_unarchive` on `data.items[]` is the pattern, unless the reports owners agree the shared change.
- **Import another module's component through its `asyncBundles` export** — a deep `Loadable(() => import('../../../../../../../../employeeProfile/...'))` inside a report table loses prop types and couples the table to another module's internals.
- **Render censored leave values through `getCensoredLeaveValue(value, accessor)` in both `DefaultReportTable` and `PreviewDataTable`** — an inline `accessor.endsWith('leave_category_name') ? ... : ...` on one surface only shows raw masked values on the other.
- **Keep `if (!widgetData && !isTableWidget) return null` in `WidgetBlock`** — rendering a table on `null` data draws an empty frame with no columns. Register `DefaultReportTable` directly rather than through a pass-through wrapper.
- **Refetch shares from the server after a share is saved** — `setPendingVisibility(savedShares.length > 0 ? 'some' : 'private')` guesses the visibility model, so the badge is wrong for public reports and never resyncs; refetch through `useGetDashboardReports().fetchData` inside `ShareReportModal`.
- **Keep the legacy `/custom_reports` routes redirecting through `CustomReportRedirect` to `/reports`** — emails and bookmarks still enter there, so removing the route breaks them until traffic monitoring shows none left.
- **Close the download modal when the export start fails** — an `onFailed` in `useDownloadReportCsv` that only calls `setDownloadError(...)` leaves the modal spinning after a complexity error; call `onStartFailed?.()`.

## Tests

- **Mock a report feature flag through Redux state, `initialState.api_calls['checkFeatureFlag/<FLAG_CODE>'] = { data: { data: { accessible } } }`, not `mockUseCheckFeatureFlag.mockReturnValue(...)`** — the hook mock skips the request-and-select path the module actually runs.
- **Assert that a payload key is absent with `not.toHaveProperty('advancedFilters')`** — `expect.not.objectContaining({ advancedFilters: expect.anything() })` passes when `advancedFilters: null` leaks, because `anything()` does not match null. For saved-filter flows, assert that `deleteSavedFilters` was not called and check the upsert body (`advanced_filters`, `filter_params: {}`), not only that the popup is hidden.
